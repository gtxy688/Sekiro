- 自研**两层 HFSM 角色框架**：命令（输入/AI）与受击走两条对称的自顶向下路由链，以返回值拦截语义替代状态类型判断，跨层查询收敛为语义化 bool 接口，保证状态树扩展不破坏调用方；

- **数据驱动 + 事件驱动**：血量/架势/招式数值全部 ScriptableObject 化，表现层（UI/相机/音效）通过 20+ 事件的静态事件总线订阅战斗数据，零轮询；配套指令预输入缓冲（0.2s）、命中顿帧、键鼠手柄双输入方案自动切换。

## 二、面试官视角：这个项目最值钱的 5 个亮点

排序原则：初级岗位面试官在找四样东西——①有没有踩过真实的工程难题 ②有没有自己的设计思考（而不是照抄教程）③代码是否经得起翻 ④会不会主动反思缺陷。以下按"单位时间说服力"排序。

### 亮点 1：命中判定（最像真实工程问题，最抗深挖）

**一句话**：高速挥砍的判定不是开关一个 Collider 就完事，是一整套"扫位移段 + 补点检 + 盖全段 + 三重去重"的组合拳。

**为什么值钱**：这是几乎每个做过动作游戏的人都会踩的坑（OnTrigger 漏检），而你的解法有四层递进，每一层对应一个具体失效场景。面试官立刻能判断你真做过、真调过。

**必然追问**：为什么不用 OnTrigger → 时序怎么保证 → 重复结算怎么防 → 拼刀双倍怎么防。全部答案在指南 Q1（已核实到代码：`Hitbox.cs` LateUpdate 扫描、三个去重 HashSet、`Hitbox.cs:168` 的 InstanceID tie-break）。

### 亮点 2：弹反系统（游戏设计 + 技术实现双重深度）

**一句话**：短按弹反/长按格挡一套输入、抖刀惩罚防连点、完美弹反自身架势永不崩——三个设计决策全部对齐原作手感，Boss 侧还有"命中瞬间做防御判定"的被动防御。

**为什么值钱**：它同时证明了游戏感和工程能力——面试官不用打开 Unity 就能从"你理解为什么这么设计"里看出你是不是真的玩过、拆过只狼。`CharacterBody.cs:969` 的 `TryPassiveDeflect`（连挡计数升级完美弹反）是全项目最不"教程味"的一块。

**必然追问**：弹反窗口怎么调 → 连点怎么防 → 被弹反后 Boss 怎么惩罚贪刀。答案在指南 Q2；反击时机那行"硬直结束 + ParryCounterHitDelay − 反击招前摇"的倒推公式（`DeflectState.cs:318` 附近）是全场最精妙的一处，务必脱稿讲。

### 亮点 3：HFSM + 双路由（架构能力证明）

**一句话**：两条对称路由链（命令链 + 受击链），"受击结算需要知道我当前在弹反吗/无敌帧吗"这类跨层查询，从"判断状态类型"变成"沿树问一圈"。

**为什么值钱**：面试官都在等候选人回答"你的状态机怎么处理受击和输入的并发"。你有现成的、经过验证的答案，还附带一条自己立的硬约束（禁止业务代码判顶层状态类型）和它为什么值得（类型判断是编译期耦合，加层会静默失效）。

**必然追问**：为什么不用 Animator 状态机 → 状态切换的 GC 问题。前者答设计自由度和查询需求（指南 Q3），后者主动认（见第四节陷阱 3）。

### 亮点 4：Boss AI 的三层结构（行为树 ≠ 教程演示）

**一句话**：Selector 五节点：保命拦截 → 交锋反击 → 喝药惩罚 → 主动抽招 → 走位，招式从 SO 表按权重 + 冷却 + 距离窗 + 条件位加权抽取，运行时烘焙成 AttackConfig。

**为什么值钱**：多数学生项目的"AI"是 if-else 或 NavMesh 追人。你的是分优先级的决策结构，且"喝药惩罚""交锋反击"体现的是**对战斗节奏的理解**——AI 服务器在惩罚玩家行为，不只是出招。

**必然追问**：树长什么样 → 招式怎么配 → 连招段间怎么切。答案在指南 Q5（树组装代码 `BTBrain.cs:202-226`，已核实）。

### 亮点 5：数据驱动 + 事件总线（工程习惯证明）

**一句话**：数值全 SO、表现层零轮询——UI 的架势条不读 `CurrentPosture`，只订阅 `OnPostureChanged`。

**为什么值钱**：这体现的是"读过别人代码、想过协作"的工程素养，恰好是大厂校招最看重的可培养性信号。

**必然追问**：静态事件泄漏怎么办 → 单例 vs SO 事件通道的权衡。答案在指南陷阱 2（答案的关键是"订阅严格写在 OnEnable/OnDisable"，这句要能脱口而出）。

## 三、项目全景回顾（带你把项目走一遍）

> 目标：让你能对任意一个系统说出"它在哪层、干什么、和谁交互、为什么这么设计"。
> 建议配合实机：开着 Unity 打一场 Boss 战，对照 3.2 的十步数据流走，比背文档快十倍。

### 3.1 先建地图：目录结构 = 分层

```
Assets/Scripts/
├── FrameWork/          ← 框架层：HFSM + CharacterBody（角色唯一门面）
│   ├── States/         ← 全部状态（Base/Hierarchical 基类 + Ground/Air/Dead 叶子）
│   └── Body/CharacterBody.cs   ← 1492 行，全项目的"总线"，见 3.4 陷阱 1
├── Combat/             ← 战斗层：Hitbox/Hurtbox/CombatManager（命中与结算）
├── SO/                 ← 数据层：CharacterConfig / AttackConfig / AttackWindowSync
├── Boss/               ← AI 层：BTBrain + BehaviourTree/ + 招式表（MoveTable/Picker/Baker）
├── Player/             ← 控制层：PlayerBrain（输入→命令）、LockOnManager、键位重绑定
├── Mgr/                ← 管理层：CombatEventBus / FXManager / GamePause / CombatInputGate
├── Camera/             ← 表现层：Cinemachine 锁定/震屏/遮挡淡化
├── UI/                 ← 表现层：CombatUIController + Views/（纯订阅的 MVC View）
└── Audio/              ← 表现层：AudioManager / BGMManager / BossVoiceDirector
```

**一句锚点记住全局**：`CharacterBody` 是所有系统的交汇点（唯一 MonoBehaviour 门面 + 状态机宿主 + 数值容器），`CombatEventBus` 是所有表现的出口，`CombatManager` 是所有命中的仲裁者。

### 3.2 一场 Boss 战的完整生命周期（十步数据流，背下来）

这是"回顾项目"的主线。每一步标注代码入口，面试时能顺着这条线白板画出来，就赢了 90% 的校招候选人。

1. **输入**：Input System 每帧 `ReadValue` → `PlayerBrain` 把按键翻译成 `ICommand`（攻击/弹反/垫步…）——注意不是立刻执行，而是 `BufferCommand` 进 **0.2s 预输入缓冲池**（`BrainBase.cs:26`，这就是"连招打出来顺滑"的原因）。
2. **命令路由**：`BrainBase.Update` 每帧调 `CharacterBody.TryExecuteCommand` → 顶层状态 `HandleCommand(cmd)`：父状态先拦（如 GroundedState 拦截跳跃等），不放行再抛给子状态机当前叶子。**返回 true = 消费**（清缓冲池），false = 留着下帧再试（`BaseState.cs:19` 的注释就是这条契约）。
3. **攻击开始**：`AttackState` 进场，把当前招的 `AttackConfig`（SO）挂到 `body.ActiveAttack` 并绑定武器 Hitbox；动画事件在 `HitStartTime` 帧开判定、`RecoveryWindowStart` 前关（`AttackWindowSync.CanMeleeHit` 是总闸门，弓段/0.01s 假窗直接不许开刀）。
4. **命中扫描**：`Hitbox.LateUpdate`（`Hitbox.cs:77`）——先 `Physics.SyncTransforms()`（动画在 Update 写骨骼，必须同步后才扫）→ `SphereCastAll(上一帧位置→当前位置)` 扫**位移段**防高速穿透 → `OverlapSphereNonAlloc` 点检防"刀已叠在目标体内漏检" → `OverlapCapsuleNonAlloc(柄→尖)` 防贴身刮过；预分配 `Collider[16]` 缓冲，热路径零 GC。
5. **分流**：扫到 Hurtbox → `TryHit`（`hitTargets` 防一刀多结算 / `blockedUntilExit` 保证连招第二刀生效）→ `CombatManager.ReportHit`；扫到对方 Hitbox → `TryClash`（`InstanceID > other.InstanceID()` 只让一方上报，防双倍拼刀架势）→ `ReportClash`。
6. **受击路由（镜像链）**：受害者 `CharacterBody.ReceiveHit` 打包 `HitData` → `OnHitReceived(hit)` 沿状态树向下问：父状态先拦（`StunnedState` 拦二次受击防硬直刷新）→ 叶子再拦（`DeflectState` 判弹反窗、`DodgeState` 0.3s 无敌帧、`MikiriCounterState` 识破突刺）。**返回 true = 拦截不扣血**；false 才扣血 + 攒架势 + 切受击状态。
7. **Boss 被动防御**：Boss 非攻击/非硬直时被命中 → `TryPassiveDeflect`（`CharacterBody.cs:969`）：普通命中 → 强制切入带 `pendingHit` 的格挡姿态；**连挡计数达 SO 阈值 → 升级 PerfectParry 弹开玩家**。这是"AI 模拟按键"到"命中即判定"的建模差异，主动讲。
8. **弹反结算**：`DeflectState.OnHitReceived`：窗口内且无抖刀惩罚（`raiseSpamGuard`，连点举刀会让窗口内也只算普通格挡）→ 完美弹反：攻击者进被弹硬直、吃架势（`allowBreak: true`）、自己架势 `allowBreak: false` 永不崩；同时置 `KengekiArmed`。
9. **反击与崩解**：`BT_Kengeki` 看到 `KengekiArmed`，在被弹方硬直结束时抽反击招——**发起时刻 = 目标硬直结束 + ParryCounterHitDelay − 反击招 HitStartTime**（按招式前摇倒推），玩家恢复后的 0.15s 出刀前摇注定晚于反击命中，贪刀必罚是数学保证；架势满 → `ForcePostureBroken`（按来源 Attack/Deflect/Mikiri 切对应受害姿态）→ `CombatManager.TryExecuteAvailableFinisher` 按崩解来源自动选忍杀演出（地面/弹反/识破），清命，两命清空 → `OnVictory`。
10. **表现广播**：以上每一步同时由静态 `CombatEventBus`（`Mgr/CombatEventBus.cs`，20+ 事件）广播——UI View 只订阅（架势条/忍杀红点/危字提示/回生选项）、`CameraShake` 用 DoTween 震屏、`AudioManager` 从 Resources 池随机播格挡/弹反音效、`BossVoiceDirector` 管 Boss 台词。**表现层没有任何一帧在轮询战斗数据**。

### 3.4 关键设计决策（"为什么"清单，面试最容易卡壳的地方）

| 决策 | 为什么 |
|---|---|
| 状态机不用 Animator 驱动 | 需要受击/命令的双向查询和复杂拦截语义；Animator 状态机拿不到"我在弹反吗"这种跨层语义，还得靠行为参数旁路 |
| Hitbox 是 Trigger 但不用 OnTrigger 回调 | Trigger 回调只在物理步进检测离散帧；扫描方案把"两帧间的连续位移"也盖住（细节见指南 Q1） |
| 受击用 struct `HitData` 打包而不是直接传引用 | 受击结算是一次性数据（谁打我/什么招/架势伤多少），值语义防止表现层持有战斗数据引用 |
| Boss 防御 = 命中即判定，而非 AI 按键 | AI 模拟按键需要预测玩家攻击帧，误差大且难调；命中瞬间判定是确定性的，且天然支持"连挡升级弹反" |
| 招式运行时烘焙而非逐招建 SO 资产 | Boss 一招含多段动画 + 多窗口伤害覆盖，逐段手工建 SO 会产生几十个资产且改一个数要开多个文件；`BossAttackBaker.Bake` 把"表条目 → AttackConfig"收敛成一处 |
| 架势回复非线性（越高回越慢） | 线性回复下 Boss 残血架势反而回得快，玩家永远打不崩；反比例制造"压着打就能崩防"的正反馈 |
| 完美弹反自身 `allowBreak: false` | 只狼的核心承诺：弹得准就绝不会因弹反而崩防——手感承诺直接写进结算参数 |
