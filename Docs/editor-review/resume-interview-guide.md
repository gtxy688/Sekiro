## 一、为什么这块仍然值得准备

校招 Unity 岗的作品集，99% 是「我做了个战斗系统 / 我搭了个框架」，面试官一天看二十份，全都长一个样。

编辑器工具稀缺，因为它证明两件别的东西证明不了的事：

1. **你踩过真实的调参痛苦**——不是从教程抄的，是被"改数值→Play→挨打→退出→再改"折磨过才动手的
2. **你知道工具是给人用的**——`AttackTimelineWindow` 里那么多 HelpBox 提示、拖拽手感、Shift 细调，都是"自己用着不舒服"留下的痕迹

但要认清定位：**它是加分项，不是主干**。面试官招你去做游戏，不是招你做工具。你的主干还是战斗系统。

## 二、哪些能讲，哪些别讲

**别把 4800 行当整体讲。** 面试官问"这些工具你跑了几次"，Builder 类答"一两次"就露馅。

| 工具 | 权重 | 理由 |
|------|------|------|
| `AttackTimelineWindow` | ★★★ 主力 | 持续使用、有真实痛点、可视化 + 3D 预览 |
| `BossMoveDamageWindow` | ★★ 配角 | 配套，讲"招式数值分层继承" |
| `CombatHUDBuilder` 的 `BakeDeathLayout` | ★★ 配角 | 不是"会生成 UI"，是"运行时动态生成 vs 编辑器预烘焙"的取舍 |
| `LockOnCameraBuilder` | ★ 一句话 | 自动装配 Cinemachine 三套机位 |
| `GenichiroMoveCatalogExporter` | ★ 一句话 | 有争议（双真值源），只在被追问"数据怎么同步"时提 |
| `DeflectSparkBuilder` / `AttackSlashBuilder` / 三个 KanjiBuilder | ✗ 不讲 | 一次性脚本，会被追问"跑了几次" |
| `ClipRenamer` / `InPlaceClipGenerator` / `BatchRootTransformSettings` | ✗ 不讲 | 同上，且逻辑偏薄 |

## 三、简历条目：三档写法（**当前不采用，仅作参考**）

### 第一档（保守）
> **攻击帧可视化编辑工具**（Unity EditorWindow / C#）
> - 自研招式判定帧编辑窗口：时间轴拖拽编辑命中窗口、音效帧、出箭帧
> - 集成 `PreviewRenderUtility` 离屏渲染 + `Animator` 逐帧采样
> - 通过 `SerializedObject` / `Undo.RecordObject` 保证编辑可撤销

### 第二档（需先补量化数据）
> - 将「改数值 → Play → 实测 → 退出 → 再改」压缩为「拖时间轴 → 看姿势 → 保存」单次循环
> - **单个判定帧调整耗时从约 40 秒降到约 5 秒**（数字必须实测）
> - 全项目 30+ 招式的判定与音效帧均通过该工具配置

### 第三档（需先补 Guard）
> - 配套自研校验体系：`AssetPostprocessor` 自动套用 FBX 导入规范、`IPreprocessBuildWithReport` 构建前拦截非法配置

> **量化数据怎么测**：挑 3 个没调过的招式，分别用两种方式调并计时，取平均。
> **诚实报数字，哪怕只有 3 倍**——3 倍配真实测量过程，比编的 10 倍有说服力。

## 四、面试追问：四层拆解

### 第 1 层：技术细节

| 追问 | 要点 |
|------|------|
| `PreviewRenderUtility` 怎么用？ | 离屏渲染到 RenderTexture，不污染主场景；**必须手动 `Cleanup()`**，否则泄漏 RenderTexture |
| 怎么采样任意时间点姿势？ | `animator.Play(state, 0, normalizedTime)` + **`animator.Update(0f)`**（不调的话编辑器里没有帧循环，Animator 不推进） |
| 怎么从状态名找 AnimationClip？ | 遍历 `AnimatorController.layers[].stateMachine` 递归子状态机，比对 `Animator.StringToHash(state.name)`；注意先解 `AnimatorOverrideController` |
| 为什么用 `SerializedObject` 而不是直接改字段？ | ① 自动进 Undo ② 支持 Prefab override ③ 多对象编辑 ④ 自动脏标记 |
| `Undo.RecordObject` 为什么要在修改**前**调？ | 它记录调用时刻的快照，改完再调等于把改后状态记为原始状态，Ctrl+Z 无效 |
| Editor 与运行时代码怎么隔离？ | asmdef 建独立程序集，Editor 程序集引用 Runtime，勾选 Editor 平台 + `UNITY_EDITOR` 约束，反向引用编译期即被拒 |

### 第 2 层：设计取舍

| 追问 | 要点 |
|------|------|
| 为什么做这个工具？ | **讲故事**：调判定帧时每次改完要 Play、等加载、触发、观察、退出，一轮 40 秒起。**核心洞察：判定帧是时间维度的信息，就该用时间维度的 UI 编辑** |
| 为什么数据存 SO 不存 JSON？ | 与运行时共用同一数据结构，无"编辑器格式→运行时格式"转换层，改完即生效 |
| 编辑中的改动什么时候写回？ | 编辑到 working 副本、点保存才写回。原因：时间轴拖拽是高频操作，每次 `SetDirty` 会让资产常驻脏状态、Undo 栈爆炸。代价是用户可能忘保存，所以要有明显的保存按钮 |
| 为什么把 UI 预烘焙进场景而不运行时动态生成？ | 运行时 `Instantiate` UI 有首帧卡顿、无法在编辑器预览调布局、每次 Play 重建。**代价**：场景文件变大、改结构要重跑工具 |
| 为什么 Postprocessor 只在首次导入接管？ | 自动覆盖用户手工调过的导入设置是最招人恨的工具行为。用 `importSettingsMissing` 判定，已有资源绝不动 |

### 第 3 层：缺陷自曝（**最高加分层**）

答"没什么不足"直接出局。挑两个真实缺陷，句式是「问题 X，在 Y 场景发现，方案 Z，因 W 排期在后」：

1. **窗口状态没做持久化**：`playerConfig`/`bossTable` 没标 `[SerializeField]`，domain reload 会清空。**已修**。
2. **早期只有生成类工具，没有拦截类机制**：招式表动画状态名写错要等 Play 才暴露且不报错。**改进方案**：构建前校验 + 导入期自动套规范。**已修**。
3. **三份 KanjiBuilder 复制粘贴**：一次性脚本没上心，加第三个时才意识到。**部分修**（抽出贴图处理，其余保留——已跑完的产物不值得为好看而动）。

### 第 4 层：工程化

| 追问 | 要点 |
|------|------|
| 工具怎么保证不出错？ | 三层拦截：导入期（AssetPostprocessor）、编辑期（体检窗口）、构建期（`IPreprocessBuildWithReport` 失败即中断） |
| 怎么测编辑器工具？ | 纯逻辑（如 `AttackWindowSync.ClampPulses`）适合 Edit Mode 单测；UI 交互靠人工验收清单；导入处理可用 `-batchmode -executeMethod` 在 CI 跑。**诚实说**：本项目只做了人工验收清单 |
| 团队协作下怎么用？ | 工具不写场景，配置走 SO 便于 diff；但 SO 多人同时改会冲突，大规模团队通常配数值表工具 |
| 重做一次会改什么？ | ① 一开始就用 UI Toolkit 而非 IMGUI（1000 行后事件处理和布局会失控）② 布局参数一开始就抽成配置 SO ③ 先做校验再做生成工具 |

## 五、三个陷阱题

**陷阱 1：「这些是不是 AI 写的？」**

原则（与 `Docs/面试准备-苇名之刃.md` 一致）：决策权在我，AI 是工具。针对编辑器加一句：

> 工具的**需求来自我自己踩的坑**，**交互形态是我定的**，AI 主要承担 IMGUI 样板代码。我能讲清每个设计决策背后的原因，包括哪些地方我否了 AI 的方案——比如 AI 一开始想做纯数值面板，我否了，因为判定帧是时间维度信息。

**关键**：承认 AI 参与，但把"决策权"讲具体。空谈"决策权在我"没用，要举出"我否掉了 AI 的某个方案"。

**陷阱 2：「4800 行工具配一个 Demo，是不是过度设计？」** ← **最狠的一题**

> 看起来多，但拆开看：A 类一次性脚本约 2500 行，跑完就固化成场景资产；真正持续使用的是 B 类两个 Window。**如果重来我会砍掉一半 A 类脚本，改用预制体模板 + 少量自动装配**。工具投入的边界要卡在"用超过三次才值得写"，这点我一开始没算清楚。

**主动承认投入产出比倒挂，反而加分**——说明你有成本意识。

**陷阱 3：「换个人能用吗？」**

诚实答：部分能。时间轴窗口 HelpBox 写得很详细；但 Builder 系列依赖"场景叫 GameScene、物体叫 Player、有 PlayerBrain/BTBrain"这些隐式约定，找不到就直接弹窗退出。**改进方向是加场景模板或资产依赖校验，而不是继续打补丁。**

## 六、当前采用的方案：不写简历，对话中带出

**原因**：见第七节的能力盘点结论——你是工具的使用者与调试者，不是设计者。写在简历上 = 邀请深挖，而深挖两层就会露。

**做法**：简历不占条目，面试时被问到"你怎么调数值""项目里有什么特别的地方"时自然带出：

> "招式判定帧一开始只能在 Inspector 里改数字，看不出对应动画哪一帧，很痛苦。后来我做了个时间轴窗口，能拖着看姿势——**这块我 Unity 编辑器 API 不熟，是边学边让 AI 辅助写的**，交互形态我自己定的。"

**最后那句主动交底是关键**：性质从"涉嫌造假"变成"知道自己边界在哪"，后者在应届生里是稀有品质。

**最低准备成本 8–12 小时**：只读懂 `AttackTimelineWindow` 一个文件 + 记住 3 个设计点 + 攒 2 个"AI 的方案被我改掉"的具体事例 + 准备一句承认边界的话。

## 七、能力盘点结论（支撑第六节决策）

2026-09-01 做了三题校准（HFSM 分层 / 全权根运动 / 招式数值怎么定的）：

| 题 | 层次 | 结果 |
|---|------|------|
| HFSM 顶层为何只装 HierarchicalState | 设计 | C+（接近 B）——答的是"目的"而非"机制"，但补充时说出"平铺会写很多 if else"，说明摸到了规则分散的核心；漏了 Hit 侧路由与查询路径一致性 |
| 全权根运动为何还要 Rigidbody | 原理 | 不及格——"影响相机跟随"不成立（Cinemachine 跟 Transform）；正解是**设 velocity 而非 position，让物理引擎有机会拒绝位移** |
| 招式判定时间怎么定的 | 经验 | **真东西**——对着动画一帧帧调；踩过「判定条缩成 0~0.01」的坑并定位根因 |

**画像：使用者 + 调试者，不是设计者。**

- 能讲：调参过程、排查 bug 的闭环、工具解决了什么问题、游戏手感判断
- 不能讲：「我设计了 HFSM 架构」「我实现了命中判定」

**但这不是坏消息**：对校招初级岗够用，因为那对应的就是初级岗。问题不在水平，在**简历的叙事层级放错了**——写"负责招式数值配置与战斗手感调试，独立排查并修复判定窗口边界 bug"，是同一件事的诚实版本，且对初级岗更有说服力（具体、可验证、有过程）。
