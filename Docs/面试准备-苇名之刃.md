### Q1. 为什么选择复刻只狼？为什么是弦一郎这战？（★★）

**考察点**：游戏理解、选型理由、拆解能力。

**答案要点**：
- 只狼的战斗系统是"回合制博弈"的教科书：每一招都有明确的应对（弹反/识破/闪避），反馈清晰（打铁声、架势条），比"无脑连招"类游戏更适合展示系统设计能力。
- 弦一郎这战有三阶段变化 + 弓术/突刺/近战混合，招式丰富度足够撑起行为树和状态机的复杂度，但又不至于像最终 Boss 那样无法完成。
- 我是先拆解机制（列出所有系统：架势、弹反、危字、处决、复活），再排实现顺序（先判定后表现、先玩家后 Boss），按模块验收推进的。

**加分句**："我只用了半天拆机制树，把'有哪些系统、依赖关系、先后顺序'列清楚才开始动手——写代码前先拆解，这个习惯帮我控制住了项目范围。"

### Q2. 你觉得这个项目里最难的模块是什么？（★★★）

**考察点**：自我认知是否真实（说"不难"是减分项）、对难点的理解深度。

**答案要点**（三选一，选你真觉得难的）：
- 命中判定的稳定性：高速挥刀不漏判、不重复结算、拼刀不双倍（详见第五部分，**推荐选这个**，因为能讲最细）。
- 处决/投技的成对状态同步：两个角色各自播动画，Clip 长度不同，谁先结束都不能提前解除，否则另一方的状态被掐断（详见第三部分 Q8）。
- 弹反窗口的"手感"调节：窗口多久、判定在哪几帧、完美弹反和普通弹反的反馈区别——这些参数全部放 SO 里反复调。

**雷区**：不要说"最难的是美术资源/动画没素材"这种非技术难点（除非真没有，但也要讲一句怎么绕过的）。

### Q3. 复刻到什么程度？哪些系统做了，哪些没做？（★）

**答案要点**：
- 做了：三择（弹反/识破/闪避）、架势与崩解、忍杀处决、危字攻击（突刺/下段）、拼刀、投技、葫芦回复、复活（回生）、Boss 三阶段（弓术/突刺/近战混合）、锁定、相机运镜与震动、完整 UI/音效。

## 三、HFSM 分层状态机（简历第二句 ★★★）

### Q4. 什么是状态机？为什么角色行为要用状态机？（★★★，基础题）

**答案要点**：
- 状态机 = "当前处于哪个状态 + 什么条件下切到哪个状态"，把角色的行为组织成离散状态（Idle/Move/Attack/Deflect…），每个状态只管自己的进入、更新、退出逻辑。
- 好处：① 行为互斥（不会一边攻击一边移动，除非设计允许）；② 切换条件集中，逻辑可读；③ 每个状态的代码独立，好改好测。
- 对比：不用状态机的话，一坨 `if (attacking && moving && !deflecting)` 的布尔组合会失控——**这就是"面条代码"**。

### Q5. 你用的是 HFSM，和普通 FSM 有什么区别？为什么分层？（★★★）

**答案要点**：
- 普通 FSM 所有状态平铺一层，攻击/受击/闪避/死亡全部平级，状态多了互相切换的条件爆炸（N×N 的连接）。
- HFSM 把状态分两层：**顶层父状态**（Grounded 地面态 / Air 空中态 / Stunned 受击态 / Dead）+ **叶子状态**（Idle/Move/Attack/Deflect/Dodge/Mikiri…），叶子状态住在父状态的子状态机里。
- 为什么分层：① 公共逻辑上提——只要在地面态，受击流转的规则就统一由 GroundedState 管；② 切换路径变短——"空中被击落"只需要顶点切换 Air→Grounded，不用管里面是哪个叶子；③ 表达自然——"地面上的攻击被打断"和"空中的攻击被打断"本来就是两种结论。
- **具体到我的实现**：父状态 `HierarchicalState` 自己养一个 `SubStateMachine`，进入父状态时自动切入默认子状态（`GetInitialSubState`），每帧驱动子状态更新，退出时强制清掉子状态。

### Q6. 命令和受击是怎么在两层状态机里路由的？（★★★，深度题）

**答案要点**（这是你项目最值钱的架构细节，讲清楚就赢了）：
- 两条路由：**Command 路由**（输入/ AI 意图）和 **受击路由**（物理命中），都是"先问父状态要不要拦截，再往下抛给当前子状态"的两级转发。
- `HierarchicalState.HandleCommand(cmd)`：第一步问父状态自己（`OnParentHandleCommand`，比如受击态二次受击要不要吞掉）；第二步抛给当前子状态处理。
- `OnHitReceived(hit)` 同理：父状态可拦截（比如 Stunned 期间不再被新受击打断），否则抛给当前子状态——**这样 DeflectState 即使藏在 GroundedState 的子状态机里，弹反判定也能被正确查问到**。
- 拦截优先级是这套路由的灵魂：父状态是"守门员"，子状态是"执行者"。

### Q7. 为什么禁止业务代码直接判断顶层状态？（★★，架构题）

**答案要点**：
- 架构红线：`MainStateMachine.CurrentState is DodgeState` 这种判断**永远为 false**（DodgeState 永远在 GroundedState 的子状态机里，CurrentState 永远是顶层父状态）。
- 所以查询/切入一律走 `CharacterBody` 的封装 API（`IsGroundedTop` / `IsInGroundedSubState<T>` / `TryChangeGroundedSubState` / `ForceChangeGroundedSubState`）。
- 为什么：① 外部代码不依赖"状态机长什么样"，依赖的是 CharacterBody 提供的语义能力（"是否在地面"而不是"当前是不是某类"）；② 以后状态机内部再怎么重组（再拆一层、改名），外部代码一行不用改；③ 跨层判断散落各处 = 状态机永远不敢重构。
- **面试金句**："我规定顶层类型判定只允许出现在 CharacterBody 内部，相当于把'状态机的地形图'藏起来，对外只暴露能力接口——这是封装，也是我留给未来重构的余地。"

### Q8. 状态切换有几种方式？（★★）

**答案要点**：
- **Command 路由**：正常行为流。Command 来自 Brain（玩家输入 / Boss 行为树选招），走 `MainStateMachine.HandleCommand` 两级路由，由当前状态决定接受还是拒绝（比如攻击硬直中不接受移动命令）。
- **直接 ChangeState**：环境/物理强制切换，不走 Command——比如受击（`ReceiveHit → OnHitReceived` 链路）、处决/投技被 CombatManager 强制拉进成对状态。设计理由："命令可以被拒绝，物理不能"。

### Q9. 玩家和 Boss 怎么共用同一套状态机？（★★★，你简历的原话）

**答案要点**：
- 框架层（共用）：`CharacterBody`（所有角色能力的中枢）+ `StateMachine` / `HierarchicalState` / 所有叶子状态类 + 受击/弹反/架势逻辑——玩家和 Boss 都是 `CharacterBody`，都挂 `MainStateMachine`。
- 特化层（各用各的）：状态构造时传入的属性和参数不同；Boss 的 Brain 是行为树，玩家的 Brain 是输入系统，两个脑子的输出都统一成 Command 走同一套状态机——**这就是"决策与执行分层"：决策层可以随便换（换 AI、换输入），执行层不用动。**

**追问：共用一套框架，会不会互相污染？** → 加一句："共用的是'行为组织方式'，不是'行为参数'。每个角色实例有自己的配置和数据（SO + 运行时状态），所以共用框架不等于共用状态。"

### Q10. 打断与优先级怎么处理？（★★）

**答案要点**：
- 用 CharacterBody 上的标志位做"可被打断性"声明：`AttackUninterruptible`（霸体，受击不打断）、`IsAttackRecoveryOpen`（收招后摇可被取消）、`IsFinisherLocked`（处决/投技期间全身锁定，不许任何外部打断）。
- 受击时状态机路由先看当前状态/父状态是否允许（拦截逻辑在 `OnParentHandleHit`），允许才切受击。
- **设计思想**："优先级不是写死的表，而是每个状态自己声明'我现在怕不怕被打'——把规则放到每个状态内部，加新招式时不用改全局表。"

### Q11. 处决/投技这种"双角色成对动画"怎么实现的？（★★★，讲出来很加分）

**答案要点**：
- 这是 `CombatManager` 存在的核心理由之一——**它持有成对的场景级状态**（这也是它用单例的正当性）：`activeFinisherPlayer` / `activeFinisherVictim`、投技的 `grabThrowAttacker` / `grabThrowVictim`。
- 流程：CombatManager 校验成立（玩家才能发起、Boss 才能被处决、范围、崩解来源匹配）→ 双方同时强行切进 FinisherState / FinisherVictimState（直接 ChangeState，不走 Command，因为是强制演出）→ 双方 IsFinisherLocked = true，期间一切输入/受击失效 → 动画播完由状态调用 `CompleteFinisherSequence` / `CompleteGrabThrow` 解锁。
- 投技的细节：双方 **Clip 长度可能不同**，所以用 `grabThrowAttackerDone` / `grabThrowVictimDone` 两个标志，**等两边都到点再一起回 Idle**——"短的一方不能把长的一方掐掉"。
- 动画名占位与校验：用 `AnimUtil.ResolveState` 解析状态，找不到会 LogError 提示——**宁可大声报错，不要静默放空动画**。

### Q12. 如果加一个新状态（比如"蓄力攻击"），你的框架要怎么改？（★★，可扩展性题）

**答案要点**：
- 落地一个 `ChargeAttackState`，放进 Grounded 父状态的子状态机；在 CharacterBody 或输入侧加触发命令；数值放新的 AttackConfig。不用改状态机框架本体、不用动其他状态。
- **面试金句**："新状态 = 新增一个类 + 一条触发路径 + 一份配置，不需要改任何已有状态——这就是我当初分层的目的。"

## 四、自研轻量行为树（简历第二句 ★★）

### Q13. 行为树是什么？和状态机什么区别？（★★★，高频对比题）

**答案要点**：
- 行为树 = 一棵树，每次从根节点 `Evaluate()` 遍历，节点返回 Running（还没完）/ Success（干完了）/ Failure（干不成）。控制节点（选择器 Selector、序列 Sequence）决定子节点执行顺序，叶子节点是具体行为/条件。
- 我的实现：`Node` 是抽象基类（`Evaluate()` 是核心），`Selector` 按顺序挑第一个能跑的（类似"优先试，不行就换招"），`Sequence` 要求全部成功（类似"先瞄准再射箭"），`ConditionNode` 做条件判断，叶子 `BT_*`（`BT_PickActive` 选招、`BT_ExecuteMove` 执行招式、`BT_MoveToTarget` 接近、`BT_HealPunish` 抓玩家喝葫芦等）做具体事；共享数据走 `Blackboard` 黑板，构建时从根注入。
- **和状态机的区别/分工**（这是面试官最爱问的）：
  - 状态机 = **"我能做什么、现在在做什么"**，状态互斥、切换明确，管执行。
  - 行为树 = **"下一步选做什么"**，带条件和优先级，管决策。
  - 我的项目里：玩家的决策来自输入（直接发 Command）；Boss 的决策来自行为树（选一个招式 → 发 Command）→ 两者统一落到同一套状态机执行。**决策层和执行层之间用 Command 解耦。**

### Q14. 为什么自研行为树，不用 Behavior Designer / NodeCanvas 插件？（★★★，必问）

**答案要点**：
- ① 学习目的：行为树的本质（遍历、节点状态、黑板）自己写一遍才算真懂，插件是黑盒；
- ② 作品集无依赖：不依赖付费/第三方插件，任何人 clone 下来直接能跑；
- ③ 需求可控：我只需要"选择器/序列/条件/黑板"这个规模，自研轻量框架完全够，还能完全掌控扩展；
- ④ 性能与调试：自己写的，出问题知道去哪找。
- **补一句诚实边界**："当然，商业项目里我大概率会用成熟的（插件或团队自研大框架），因为别人维护过的轮子更稳——自研是为了学，不是为了炫。"

### Q15. 行为树和状态机怎么衔接的？（★★）

**答案要点**：Boss 的行为树选完招（`BT_PickActive` 从招式表 `BossMoveTable` / `GenichiroMoveCatalog` 里挑）→ 产出招式/意图 → 转成 Command 或直接走状态机切换 → 状态机执行动画、判定、表现。**行为树不直接碰动画和判定，它只输出"意图"。**

### Q16. Boss 的招式怎么编排的？（★）

**答案要点**：招式数据化（招式表 + 招式条目，AttackConfig 携带伤害/危字/击退等），行为树按优先级和条件选招（比如玩家喝葫芦 → HealPunish 惩罚行为；玩家弹反成功 Kengeki 剑戟窗口 → 特定应对；距离远 → 弓术，近身 → 连招）。Boss 有多阶段（弦一郎三阶段：弓神/突刺/血条变化），阶段切换改变行为树入口或参数。

### Q17. 行为树怎么调试？（★）

**答案要点**（诚实 + 方法）：
- 节点状态日志（Running/Success/Failure 打印）、ConditionNode 的条件打点、黑板上关键变量的运行时观察；用 Unity 的调试器断点看 Evaluate 调用栈。
- **加分句**："我的树规模不大（十来个节点），日志+断点够用；如果树复杂到上百节点，我会做运行时可视化面板——这也说明框架的扩展点在哪。"

## 五、命中判定：动画事件 + BoxCast/SphereCast 连续扫描（简历第三句 ★★★ 全简历最锋利）

### Q18. 为什么不用 OnTrigger？碰撞体触发有什么问题？（★★★，必问）

**答案要点**：
- 物理引擎按**固定时间步长**（默认 0.02s）离散采样，不是连续检测。两个高速物体之间如果相对速度足够快，一帧之间可能"互相穿过"而碰撞体从未重叠——**触发器就漏了**。只狼里挥刀速度极快（一个挥砍动画可能就 4~6 帧），漏检率高。
- 触发器还得依赖碰撞体形状调参、依赖物理引擎的触发生命周期（Enter/Stay/Exit 的时序），对"命中"这种要精确到帧的需求不可控。
- **我的方案**：每帧记录武器位置，用 SphereCast 从**上一帧位置扫到当前帧位置**，把"这段位移扫过的空间"当作判定体积——从原理上消灭穿透漏检。

### Q19. 面试官要是说"开枪射箭这种高速弹道用 Raycast 不就行了"，你怎么答？（★★）

**答案要点**：区分两种物体：
- 弹道/射线类（子弹、箭矢）：没有体积语义，`Raycast` 一条线就够了（我的箭矢就是球形扫掠 + `arrowCastRadius`）。
- 挥砍类（武器有体积、有长度、会贴身/会刮擦）：用**球体扫掠**（SphereCast，覆盖武器的粗细）甚至**胶囊扫掠**，因为剑是一个"有体积的棒状物"，不是一条线，刀身中段扫过目标也该命中。
- "从柄到尖"的覆盖：我还加了 OverlapCapsule 从刀柄扫到刀尖（`shaftRadius`），处理"贴身站在挥砍内侧，刀尖从身侧刮过"的场景。**面试金句**："判定体积要匹配武器的语义形状：线状弹道用射线，棒状武器用球/胶囊扫掠。"

### Q20. 整个命中判定的流程讲一遍？（★★★）

**答案要点**（按数据流背）：
1. **动画事件开判定**：Clip 上某个帧发事件（命中窗口在 AttackConfig 里配：`HitStartTime`/`RecoveryWindowStart`/`hitPulses`，并由 `AttackWindowSync.CanMeleeHit` 校验——防止 Clip 残留事件在非攻击段误开刀）。
2. `Hitbox.Enable()`：绑定本招式的 `AttackConfig` → `Physics.SyncTransforms()`（动画在 Update 写骨头、物理在固定步进同步，不同步会扫到旧位置）→ 记录 `lastCastPos`。
3. **LateUpdate 扫描**（每帧）：`SphereCastAll(lastCastPos → 当前位置)` 扫掠 + OverlapSphere/Capsule 点检补漏 → 命中的 Collider 找 `Hurtbox`（打人）或另一方 `Hitbox`（拼刀）。
4. **去重**：`hitTargets`（一次挥砍对同一目标只结算一次）、`blockedUntilExit`（连招处理：开判定时已叠在刀上的目标先不算，离开后再扫进来才算新的一刀）、`clashedPartners` + InstanceID 小者上报（拼刀双方都会扫到对方，只让一边上报，避免一帧双倍结算）。
5. **上报仲裁层**：`CombatManager.Instance.ReportHit(hitbox, hurtbox, point)`——**Hitbox 不直接打人**，只报告。
6. **仲裁与结算**：CombatManager 查全局规则 → 伤害数据全部取自 `hitbox.Config`（AttackConfig）→ `target.ReceiveHit(...)`（伤害/架势/危字/击退/受击等级一起传入）→ 状态机受击路由 + 事件总线广播表现。
7. **触发顿帧**（打击感）：命中/拼刀/弹反后 `HitStop()`。

### Q21. SphereCast 从碰撞体内部出发会漏，你怎么处理的？（★★，细节题，能答出来就是深度）

**答案要点**：SphereCast 的起点如果在目标碰撞体内部，会直接错过（扫掠从内部开始不检测内部物体），而**连招时第二刀经常刀还叠在目标身体里**。所以扫描分两步：扫掠（位移路径）+ 每帧**点检**（OverlapSphere/OverlapCapsule 查当前位置重叠），点检命中的同样走 TryHit——路径扫 + 位置检互为补充。

### Q22. 为什么用动画事件开关判定，而不是每帧检测"动画播到第几帧"？（★★）

**答案要点**：
- 动画事件是**挂在 Clip 本身上的数据**：谁做的动画、什么时候该出刀，由动画/剪辑说了算，代码不需要知道"第几帧该开"——**判定时机跟着美术走，而不是跟着代码猜**。
- 出刀、入鞘、位移、发箭这种"动画里程碑"用事件表达，代码侧只关心"收到事件做什么"。
- 对比轮询检测动画时间：代码要硬编码帧号/时间点，动画一改就错位。

### Q23. 拼刀（打铁）是怎么判定的？（★★）

**答案要点**：双方 Hitbox 同时开启且互相扫到 → `TryClash`（去重后只让 InstanceID 较小方上报）→ `CombatManager.ReportClash`：**不打伤害**，双方各按对方招式的 PostureDamage 涨架势（可配 `clashPostureMultiplier` 系数）→ 广播打铁事件（音效/火花）。**设计点**："拼刀是'判定成立但不掉血只涨架势'的第三种结果，和命中、弹反并列为三路分支。"

### Q24. 这个方案有什么代价/坑？（★★，主动说代价）

**答案要点**（面试官不问你也可以补一句）：
- 物理查询每帧多几次 SphereCast/Overlap，有开销——所以只在 `isActive`（判定窗开启）时扫描，平时零开销；
- 判定参数（castRadius/shaftRadius/targetLayers）要手工调，武器形状复杂时调参成本高；
- 依赖 `Physics.SyncTransforms` 的时机，动画和物理的同步顺序必须对（LateUpdate 先 Sync 再扫）；
- **触发器的优势**也要承认：省代码、事件语义（Enter 一次）现成；我选扫描换取"帧精确 + 防穿透"，代价是调参与性能自担。

## 六、数据驱动：ScriptableObject（简历第四句 ★★）

### Q25. ScriptableObject 是什么？和普通 class、MonoBehaviour 什么区别？（★★★）

**答案要点**：
- SO = 一种**不挂在场景里、而是存成资产文件（.asset）**的类：数据只存一份，全项目共享；不随场景销毁，跨场景存活。
- vs 普通 class：普通 class 是内存里的临时对象，不序列化不落盘；SO 的实例是资产，改动保存到项目里。
- vs MonoBehaviour：Mono 必须挂 GameObject、活在场景里、每份场景一份；SO 活在项目文件夹、一份全局共享、不占场景开销。
- **一句话**："普通 class 是临时纸片，MonoBehaviour 是场景里的演员，SO 是项目里的档案册——数值这种'人人都要读、谁也不要改'的数据放档案册。"

### Q26. 为什么数值全部走 SO 而不是硬编码？（★★）

**答案要点**：① 改手感不用改代码重编译——Inspector 里拖数值、调完直接试；② 一份配置多处引用（玩家和 Boss 都能挂同一份招式配置）；③ 数据与逻辑分离，代码里没有魔法数字；④ 场景/存档不背数值。**项目红线**："伤害数据只允许出现在 AttackConfig，Hitbox 里硬编码伤害属于架构违规。"

### Q27. 你的 AttackConfig 里有哪些字段？举个招式的例子？（★）

**答案要点**：BaseDamage（血量伤害）、PostureDamage（架势伤害）、PerilousType（危字类型：突刺/下段）、Knockback（击退）、HitGrade（受击等级）、hitPulses（多段命中）、HitStartTime/RecoveryWindowStart（判定窗口）。例子：Boss 的危字突刺 = 高 PostureDamage + Perilous 标记，命中玩家走"识破后可反制"分支；普通连招 = 低伤高架势积累。

### Q28. SO 有什么坑？你碰到过吗？（★★）

**答案要点**（主动说代价）：
- ① 运行时改资产值会污染设计数据（所以运行时不要写 SO，要写就写在运行时副本/存档）；
- ② 资产文件多了不好管理 → 用命名规范和分类目录（角色配置/招式配置分开放）；
- ③ 团队协作时同一资产文件容易 git 冲突（数值字段多，两人同时调参就冲突）——**这里可以自然引出**"所以团队项目里数值表常配合配表工具/数据库"，展示视野。

## 七、事件总线（简历第四句 ★★★）

### Q29. 事件总线是什么？解决什么问题？（★★★）

**答案要点**：
- 事件总线 = 一个"广播站"（发布-订阅）：产生事件的一方只负责 `TriggerXxx`，不持有任何订阅者引用；订阅方（UI 血条、音效、相机）在 OnEnable 时说"我要听"，收到广播后自己反应。
- 解决的问题：**依赖方向倒转 + 零轮询**。战斗逻辑不需要知道"UI 怎么画血条"，UI 也不需要每帧去查"血量变没变"——值变了事件推给你。
- 你的项目：`CombatEventBus` 静态类，20+ 事件（HP/架势变化、崩解、忍杀机会、相机震动、打铁音效、处决生命周期……），订阅方全是 UI/相机/音效这类表现层。

### Q30. 为什么表现层用事件而不是直接调用/轮询？（★★）

**答案要点**：
- 直接调用：战斗逻辑要持有 UI/相机/音效的引用，耦合爆炸，加一个新表现（手柄震动、飘字）就要改战斗代码；
- 轮询：每帧查一堆值变化，浪费 + 代码分散；
- 事件：战斗逻辑"喊一嗓子"就完了，加新表现 = 新写一个订阅方，战斗代码零改动。**金句**："战斗模块是发布者，表现模块是订阅者，两者之间只有事件契约，没有引用。"

### Q31. 为什么你的事件总线是静态类而不是单例？（★★★）

**答案要点**（三件套完整版）：
- 为什么静态：它是**无状态的广播站**——不需要生命周期、不需要 Inspector 配置、不需要被替换/继承，静态类是最小形态；给它套单例（`EventBus.Instance.OnXxx +=`）只是多写一层，没有能力增益。
- 对比 CombatManager 为什么是 MonoBehaviour 单例：它**持有成对的场景状态**（处决双方、投技双方完成标志），还要拖场景引用、跑顿帧协程、场景切换做清理——单例 + MonoBehaviour 两个决策叠在一起（单例管唯一，Mono 管生命周期）。
- 代价：静态事件跨场景存活，订阅不配对会泄漏（详见 Q33）。
- 升级条件：多人协作/项目变大 → 换 SO 事件通道 + RuntimeSet（详见 Q34）。

### Q32. 事件和直接调方法的区别？事件里传什么数据？（★★）

**答案要点**：事件是"通知 + 数据快照"：`OnHPChanged` 直接带当前血量/最大血量，`OnAttacked` 带伤害值——**订阅方拿到数据就能画 UI，不需要回头去查 CharacterBody 内部字段**。契约上禁止表现层读战斗模块的内部状态，这就是"表现层只靠事件总线"这条红线的含义。

### Q33. 静态事件的泄漏问题？你怎么防的？（★★★）

**答案要点**：
- 泄漏原理：`+=` 订阅后，事件会**持有订阅方的引用**（委托指向订阅方法所属对象）。如果对象销毁了却没 `-=`，它被事件"拽住"，GC 永远收不掉 → 内存泄漏；而且跨场景后事件还残留旧订阅，广播可能调到已销毁对象 → 报错。
- 防法（项目红线）：**所有订阅严格写在 `OnEnable`/`OnDisable` 里配对**——OnDisable 在销毁前一定被调用，等于"离场前把名字从名单上划掉"。
- **金句**："静态事件像借钱：有借（+=）必须有还（-=），我在 OnEnable/OnDisable 里强制配对，从生命周期上保证没有一笔烂账。"

### Q34. 如果项目变大，事件总线怎么升级？（★★★，成长性问题）

**答案要点**：换 **SO 事件通道（Event Channel）+ RuntimeSet**：
- SO 事件通道 = 把"每个事件"做成一个资产文件，发件人和收件人都持有同一资产引用，**谁和谁连着在 Inspector 里一眼可见**（依赖可视化，新人接手看场景图就懂），还能在资产上挂参数；
- RuntimeSet = 把"当前场景活着的角色"做成 SO 清单，角色 OnEnable 注册/OnDisable 注销，锁定系统找最近敌人直接查清单，不用拖引用/Find——解决"敌人多了怎么找目标"；
- 代价要知道：事件一个一资产（资产爆炸）、每个监听者手动拖线、C# 泛型 SO 不能直接建资产要写子类。**"收益是依赖显式化，成本是资产和拖线，团队项目里这笔账划算。"**
- 另外对比一下第三方：UniRx/R3（响应式流，能组合事件）、MessagePipe（DI 事件管道）、UnityEvent（可序列化但性能差，适合 UI 按钮）——说出名字就显示视野。

## 八、打击感（口头加分项 ★★）

### Q35. 顿帧（HitStop）怎么实现的？（★★）

**答案要点**：命中/弹反/拼刀时 `CombatManager.HitStop()` → 协程里 `Time.timeScale = 0.05f` 停 0.05s → 用 `WaitForSecondsRealtime` 恢复（**不能用 WaitForSeconds，因为它受 timeScale 影响，会永远等不完**）→ 恢复时检查暂停状态：如果游戏正被暂停，保持 0 而不是拨回 1（防冲突）。可开关（`enableHitStop`），全局统一入口，不散落。

### Q36. 相机震动怎么做？（★）

**答案要点**：事件总线广播 `OnCameraShake(intensity)`，相机模块自己决定怎么抖（位移/旋转噪声，强度参数衰减）。处决 1.0、投技 0.45——数值在表现层配置，战斗逻辑不知道相机怎么抖。

### Q37. 你调"手感"的流程是什么？（★★，面试官爱听）

**答案要点**：参数全在 SO（顿帧时长、架势系数、判定窗口、击退力度）→ Unity 里改完数值直接重试（不用重编）→ 对照原版节奏反复验证——**"手感是调出来的，不是写出来的，所以我把所有可调参数从代码里抠出来放进了配置。"**

### Q38. 弹反（Deflect）系统设计？（★）

**答案要点**：防御窗口内受击 → 判定成功（普通弹反/完美弹反，`DeflectType`）→ 双方架势涨 + 打铁反馈 + 是否触发剑戟（Kengeki）窗口；连续被弹反（`ConsecutiveTimesParried`）有惩罚/被反打逻辑；弹反成功还有处决机会（`FinisherReadyState`）。弹反是只狼战斗的灵魂，能展开 30 秒不重样。

## 九、战斗机制细节（简历第一句"弹反/闪避/架势崩解/忍杀处决"的深挖弹药）

### Q43. 闪避（垫步）怎么实现的？无敌帧怎么处理？（★★★，简历"闪避"）

**考察点**：移动实现方式、无敌帧的实际处理、和识破的关系。

**答案要点**：
- **全权根运动**：垫步的位移完全由动画 Root 曲线驱动（动画说滚多远就滚多远），代码只负责计时（`DodgeDuration` 到了就退出）和转向。好处：位移和动画天然同步，不会滑步。
- **无敌帧**：进垫步后 `DodgeIFrame` 秒内，`OnHitReceived` 直接返回 true 拦截——**受击路由走的是"先问状态要不要拦"，无敌帧就是 DodgeState 的拦截逻辑**，不是物理上的无碰撞，是"我免疫这次受击"。
- **锁定四向垫步**：锁定状态下相对 Boss 分前/后/左/右四向动画（用朝向点积判断），并且 `SetSuppressRootYaw(true)` 压住 Root 旋转、用代码 SnapYaw 转向——因为 Root 的 yaw 和代码转向打架会滑步/拧身。
- **识破衔接**：无方向垫步 + 突刺危字 → 直接切 `MikiriCounterState`（踩刀反制）；带方向的垫步（包括后垫）只走无敌帧，不触发识破——"防止后垫踩刀把 Boss 拧成反向"（注释原话，讲出来就是细节）。
- **互动细节**：垫步中 `HandleCommand` 只更新移动意图不打断垫步（垫步不可打断），结束时再按输入方向决定进 Move 还是 Idle。

### Q44. 识破（Mikiri）判定逻辑（★★，只狼玩家必问）

**答案要点**：
- 触发条件三件套：① 正处于垫步（DodgeState）；② 进垫步瞬间无方向输入（`mikiriEligible`）；③ 来袭判定是 `isPerilous` 且类型为 **Thrust（突刺）**。
- 满足 → 从垫步切 `MikiriCounterState`：踩刀动画 + 敌方被反制的硬直/架势大涨 → 这条链最终能接 **Mikiri 处决**（崩解来源 `PostureBreakSource.Mikiri` → 处决类型 `FinisherKind.Mikiri`，动画名 "Finsher_Mikiri"）。
- 设计点："识破只看'进垫步时有没有方向'，不看垫步动画叫前还是后"——语义输入决定资格，而不是动画状态，避免动画命名的隐式耦合。

### Q45. 架势（Posture）系统完整讲一遍？（★★★，简历"架势崩解"）

**考察点**：核心系统理解、数值循环、崩解后的状态编排。

**答案要点**（按数据流转）：
- **概念**：架势 = "防御姿态的耐力"。挨打、防御、招架都会涨；满了进崩解（处决窗口/倒地硬直）。只狼战斗的节奏就是"涨对方架势 → 崩解 → 处决"。
- **数值归属**：`CombatStats` 模块统一管 HP/架势/葫芦/复活/命数，初值全部从 `CharacterConfig`（SO）读——典型的数据驱动。
- **累计与崩解**：`AccumulatePosture` 是唯一入口：涨架势 → 广播 `OnPostureChanged`（UI 血条靠它）→ 满则置 `IsPostureBroken` + 记录 `PostureBreakSource`（Attack/Deflect/Mikiri，决定处决类型）→ 广播 `OnPostureBroken` + `OnFinisherOpportunityChanged` → 通过构造注入的 `onPostureBreak` 委托让 Façade 编排状态切换（玩家：击飞倒地；Boss：进入处决窗口）。
- **架构点（讲出来加分）**："数值模块不碰状态机——它只负责数值和广播，状态切换通过注入的委托请求 Façade 编排（'模块请求、Façade 编排'），所以数值逻辑可以独立测试。"
- **回复规则**（三条细节）：① 停止受击 `PostureDecayDelay` 秒后才开始自然回复（`UpdatePostureDecay` 每帧算）；② 按住格挡回复 ×5（`GuardPostureRecoveryMultiplier`）；③ Boss 用**非线性反函数回复**（`PostureDecayInverse`：架势越高回得越慢）——这是故意的手感设计："Boss 越接近崩解越难回血，玩家能看到压进去的希望。"
- **只狼规则还原**：完美弹反时自己的架势**永不崩防**（`allowBreak=false` 分支）。

### Q46. 忍杀处决的触发条件和流程？（★★★，简历"忍杀处决"）

**答案要点**：
- **触发前置**：Boss 崩解（`IsPostureBroken`）→ 广播忍杀机会（UI 红点 `OnFinisherOpportunityChanged`）。
- **类型匹配**：崩解来源决定处决类型——Deflect 弹反崩解 → 弹反处决（"Finsher_Deflect"）；Mikiri 识破崩解 → 识破处决（"Finsher_Mikiri"，兼容 "Finsher_Miriki" 拼写）；普通攻击崩解 → 地面处决（"Finsher_Ground"）。
- **校验链**（`CombatManager.TryExecuteFinisher`）：只有玩家能发起（`initiator != PlayerRef` 直接拒绝）、Boss 才能被处决、不能自处决、发起者自己不能处于崩解、不能已有处决在进行——**身份断言全部显式写出来**。
- **距离门**：地面处决有 `finisherRange` 距离门；弹反/识破处决**不卡距离**——因为"弹反/识破确认窗口里双方已经贴身演完反制"，再用距离门会误杀连招（注释原话）。
- **成对演出**：双方同时强切 `FinisherState` / `FinisherVictimState`（强制走 ChangeState 不走 Command），双方 `IsFinisherLocked`，动画事件驱动到 `ExecuteFinisher` 清一条命（`ClearLife`：还有命 → 回满清架势接着打；没命 → `TriggerVictory` 胜利），最后 `CompleteFinisherSequence` 双方一起解锁回 Idle。
- 防呆：动画状态缺失直接 `LogError` 报错并拒绝处决——"宁可大声报错，不要播空动画"。

### Q47. 弹反（Deflect）系统深度补充（★★★，简历"弹反"）

**答案要点**：
- **入口**：防御姿态下受击（防御的收招/前摇都可能是窗口），命中结算走 `ReceiveHit` → 状态机受击路由 → DeflectState 判定是否弹反成功（窗口参数在 CharacterConfig/AttackConfig 里配）。
- **普通 vs 完美**：`DeflectType.Normal / Perfect` 两条反馈链：音效（普通浅色打铁 / 完美深色打铁）、火花、以及后续收益差异（完美弹反自己不涨架势）。
- **结果链**：弹反成功 → 对方架势涨 + 自己被弹方出现硬直/破招 → 连续弹反计数 `ConsecutiveTimesParried` 上升（连续被弹会被反打/惩罚，防止玩家无脑弹）→ 弹反崩解 → 弹反处决机会（`FinisherReadyState` 就是这个窗口）。
- **剑戟（Kengeki）**：弹反后进入剑戟窗口（`KengekiArmed`），双方在窗口内再博弈一次，成功后有更大收益——这是只狼"防反后继续攻防"的还原。
- **为什么弹反手感好**：窗口要"看起来紧、实际松"，判定帧和动画的错位是调出来的；所有窗口参数都在配置里，调手感不动代码。

### Q48. 简历措辞风险：BoxCast ⚠️（必须处理，不然会当场穿帮）

**⚠️ 事实核查**：你简历写"**BoxCast / SphereCast** 连续扫描"，但实际代码里用的是 **SphereCastAll（球体扫掠）+ OverlapSphere / OverlapCapsule（重叠点检）**，并没有用 BoxCast。

**两个处理方案（二选一）**：

- **方案 A（推荐）：简历措辞改为真实实现**——"动画事件 + **SphereCast / Overlap 连续扫描**"。简历 = 实现，任何追问都对得上。
- **方案 B（保留 BoxCast）：必须准备故事**——"我一开始试过 BoxCast 盒子扫掠，但盒子有朝向、挥刀旋转后判定体积和刀身对不齐，而且对齐盒子要每帧算朝向矩阵；武器是棒状的，球体/胶囊扫掠没有朝向问题、更贴形状，所以换成了 SphereCast。"（**只有你真试过 BoxCast 才能这么说，没试过就选方案 A，别编**）

**无论哪个方案都要能答**：BoxCast 和 SphereCast 的区别 = 盒子扫掠（有朝向、需要对齐）vs 球体扫掠（无朝向、天然对称）；棒状武器用球/胶囊，弹道用射线，这是"判定体积匹配武器语义形状"的原则。

## 十、表现层与生命周期（UI / 相机 / 复活 / 音频 —— 简历外，但追问"还有哪些系统"必提）

### Q49. UI 系统怎么组织的？血量条怎么更新的？（★★）

**考察点**：UI 架构、事件驱动落地、"零轮询"的具体证据。

**答案要点**：
- **MVC 分层**：`CombatUIController` 是 Controller，只做"事件 → View"的转发（注释原话："不持有业务逻辑、不做每帧轮询"）；`Views/` 下每个 UI 元素一个 View（BossPostureBarView 架势条、PlayerStatusView 血条、PerilousWarningView 危字、LockOnIndicatorView 锁定点、HealKanjiView 葫芦"治"字、ReviveKanjiView "回生"字、GameOverView、VictoryView……），View 只管画自己。
- **数据流**：战斗数值变化 → `CombatEventBus` 广播（OnHPChanged 等，**事件直接携带当前值/最大值**）→ Controller 转给对应 View 更新。**表现层永远不反向查战斗模块的内部字段**——这就是"零轮询"字面意义上的落地。
- **生命周期**：Controller 在 OnEnable 注册 13 个事件、OnDisable 全部退订——**这正是 Q33 静态事件防泄漏红线的活例子**，面试官问"你项目里 OnEnable/OnDisable 配对具体怎么写的"就指给他看这个类。
- **小细节**：分流玩家/Boss 事件用 Controller 上 Inspector 拖的两个角色引用（`playerBody`/`bossBody`），而不是用字符串/枚举条件——引用优先于标记。

### Q50. 相机系统怎么做的？（★★）

**答案要点**：
- **基座**：Cinemachine 轨道相机 + `CinemachineOrbitInput`（锁定状态下按键环绕目标旋转视角——只狼锁定战的视角操作感）。
- **遮挡处理**：`CameraObstacleFader` 做障碍物淡出——相机贴近墙壁/柱子时把遮挡物材质淡掉，避免"镜头穿墙看内脏"。
- **震动**：`CameraShake` 订阅 `OnCameraShake(intensity)`，用 DOTween 的 `DOShakePosition`，时长/幅度 = 基础参数 × 强度（弹反小抖、崩解大抖、处决强抖，强度由触发方定）。
  - **这里有个好故事**："我特意没用 Cinemachine Impulse 做震动——Impulse 要配 Noise Profile 资产和响应器，对'按强度抖一下'这种需求是杀鸡用牛刀；自己十行 DOTween 搞定，还零配置。"（对比方案 + 取舍，加分）
- **运镜事件**：处决特写（OnFinisherStarted 带动镜头）、Boss 跳劈突刺的镜头上抬跟随（OnJumpThrustCamera active/boss/地面 Y）、锁定切换（OnLockOnChanged）——**相机也是纯粹的事件订阅方，战斗逻辑不知道相机存在**。

### Q51. 复活（回生）系统完整流程？（★★★，只狼标志性系统，面试官很吃这套）

**考察点**：完整链路讲述、状态机与数值模块的配合、只狼机制还原。

**答案要点**（按时间线背）：
1. **死亡触发**：HP ≤ 0 → `CombatStats.HandleDeath`：先清攻击状态/关武器判定，然后看剩余复活次数（初值来自 CharacterConfig 的 `ReviveCount`，数据驱动）。
2. **分叉**：有次数 → 广播 `OnReviveAvailable`（画面开始变暗），走 `onDeath(true)` 委托让 Façade 切 `RevivePendingState`；没次数 → 广播 `OnDeath`，直接真死（`GameOverState` / Boss 则胜利结算）。
3. **倒地待机**（RevivePendingState）：倒地动画 → 躺平"Deading"动画 → **倒地计时 1.2s 走完才弹回生选项**（`TriggerReviveChoiceReady`）。注释原话："等倒地时长走完再开选项，避免动画提前结束时变暗期间就能按键"——防"手速党在演出中偷按"。
4. **选择**：回生选项出现后，攻击指令 = 复活（1.5s 爬起动画 → 回 Grounded）；防御指令 = 就此死去（真死）。**设计点："复活是一个需要玩家倒数秒内主动按键确认的交互，不是自动的"——还原只狼'按不按'的灵魂时刻。**
5. **复活结算**：`Revive()`：扣一次复活次数 → 回满血 + 架势清零（用户决策：直接回满）→ 广播 HP/架势/复活事件（UI 隐藏回生提示）→ 顺带重置 Boss 的连续弹反计数（防"靠回生逃惩罚"）。
6. **架构点（和金句通用）**："死亡只发生在 CombatStats 的数值层面，切状态是 Façade 通过注入的委托编排的——数值模块不碰状态机，这条规则在死亡/崩解两条链路上都成立。"
- 顺带：Boss 也有复活相关编排（`BossReviveBackoffState`），弦一郎的"再战"氛围就是它给的。

### Q52. 音频怎么做的？（★，一句话弹药）

**答案要点**：战斗音效全部走事件：`OnAttackSfx` 广播 **AudioClip + 世界坐标**（"clip 由 AttackSfxCue 经事件传入，表现层不持有资源"——音频库不依赖战斗数据，还能按需加载）、打铁声 `OnWeaponDeflected`、Boss 台词 `VoiceLineView`/`BossVoiceDirector`（播放在 UI Controller 里自动挂载，旧 HUD 也能出声）。**音频模块和相机一样：订阅事件，零耦合。**

## 十二、追问链模拟（自己演练：面试官连追三层）

### 追例题 1：事件总线线（从简历词出发）

> 面：你写了"事件总线解耦"，说说事件总线是什么？
> 你：发布-订阅的广播站，表现层订阅，战斗逻辑只广播（Q29）。
> 面：为什么用静态类不用单例？
> 你：无状态广播站，静态是最小形态；CombatManager 有状态才做单例（Q31）。
> 面：静态事件不是容易泄漏吗？
> 你：+= 必须配 -=，我的订阅全部 OnEnable/OnDisable 配对（Q33）。
> 面：那如果项目几十个人一起做，你还会这么写吗？
> 你：会换 SO 事件通道，把依赖可视化到 Inspector，让新人看场景图就懂；代价是资产和拖线，团队规模上来了这笔账划算（Q34）。

### 追例题 2：命中判定线（从"不用 OnTrigger"出发）

> 面：为什么不用 OnTrigger？
> 你：固定时间步长 + 离散采样，高速挥刀会穿透漏检（Q18）。
> 面：那你怎么保证不漏？
> 你：上一帧位置到当前帧位置的 SphereCast 扫掠，把位移路径变成判定体积；再加每帧点检补内部漏检（Q20/Q21）。
> 面：这个方案有什么开销？
> 你：只在判定窗开启时扫描，平时零开销；判定参数手工调，动画/物理同步顺序要正确（Q24）。
> 面：换你你会不会用触发器？
> 你：看需求——弹道类用射线，武器类用扫描；触发器省代码但我需要帧精确，所以选扫描（Q19）。

### 追例题 3：架构线（从"玩家 Boss 共用状态机"出发）

> 面：玩家和 Boss 共用状态机，怎么个共用法？
> 你：都是 CharacterBody，都挂 MainStateMachine；差别只在 Brain（输入 vs 行为树）和参数（Q9）。
> 面：行为树选的招怎么执行？
> 你：行为树只输出意图（Command），状态机负责执行，决策层和执行层靠命令解耦（Q15）。
> 面：为什么决策和执行要分开？
> 你：决策层可以随便换（换 AI 算法、换输入设备）而执行层纹丝不动；状态机管"行为互斥与切换"，行为树管"带优先级的选择"，职责不同硬揉一起会互相拖累（Q13）。

### 追例题 4：战斗机制线（从简历第一句"弹反/架势/处决"出发）

> 面：说说你的架势系统怎么设计的？
> 你：数值集中在 CombatStats 模块统一结算，初值全从 SO 读；涨架势唯一入口是 AccumulatePosture，满了进崩解并广播事件；回复做了延迟 + 格挡加速 + Boss 反函数三条规则（Q45）。
> 面：崩解之后呢？
> 你：崩解来源决定后续——玩家崩解被击飞倒地，Boss 崩解进入处决窗口；来源还决定处决类型（弹反处决/识破处决/地面处决）（Q46）。
> 面：处决时两个人动画怎么同步的？
> 你：CombatManager 持有成对状态，双方强切处决状态并互相锁住，等动画事件驱动清命后一起解锁回 Idle；投技还处理了双方 Clip 长度不同的问题（Q11）。
> 面：你简历写的 BoxCast，为什么后来文档里全是 SphereCast？
> 你：（按 Q48 方案 A 或 B 回答——这是你最容易翻车的一题，务必提前想好）

### 追例题 5：表现层线（从"你项目除了战斗还有啥"出发）

> 面：除了战斗系统，还有什么模块？
> 你：UI、相机、音频三个表现层模块，全部走事件总线订阅；还有复活（回生）系统（Q49~Q52）。
> 面：UI 血量条怎么更新的？
> 你：从来不轮询——战斗结算时事件带当前值广播出来，Controller 转给 View 直接画（Q49）。
> 面：相机震动也是事件？
> 你：对，OnCameraShake 广播强度，相机模块自己决定怎么抖；我特意没用 Cinemachine Impulse，因为按强度抖一下的需求十行 DOTween 就够，零配置（Q50）。
> 面：复活系统讲讲？
> 你：死亡只发生在数值层，切状态由 Façade 编排；倒地 1.2s 后才弹选项防按键早抢，攻击=复活/防御=真死，回满血清架势（Q51）。

## 附：答题心法速查

1. **三件套**：为什么这么选（理由）→ 代价是什么（清醒）→ 什么条件下换（成长）。答任何架构题先想这三句。
2. **不吹不贬**：不说"单例不好我知道"，说"我权衡过"；不吹"我的方案最完美"，主动报代价。
3. **数据流优先**：被问实现细节时，先讲数据流（谁→谁→谁），再讲为什么。你的项目每条链路都有清晰的数据流（动画事件→Hitbox→CombatManager→ReceiveHit→事件总线）。
4. **诚实画边界**：不会的（Shader、图形学、多线程）主动说"我了解概念但没深入"，比被逼问出来体面。
5. **AI 问题不慌**：决策权在我、AI 是工具、我能讲清每一行。
6. **简历即战场**：面试官的问题九成从简历那四句话出发，这四句话的弹药就是本文档——复习重点是第三（HFSM）、第五（命中判定）、第七（事件总线）三章。
