## 1. 已知代码入口与尚未证明的结论

- [PlayerBrain.Update](../../Assets/Scripts/Player/Brain/PlayerBrain.cs)：持续发送 `MoveCommand`，是值类型到接口转换的检查点。尚未测量目标后端中的每帧分配。
- [Hitbox.LateUpdate](../../Assets/Scripts/Combat/Hitbox.cs)：调用 `SphereCastAll`、`SyncTransforms`；Overlap 使用 16 项缓冲。尚未证明它是帧耗时主因，也未验证密集碰撞体下的容量边界。
- [WeaponController.SpawnArrow](../../Assets/Scripts/FrameWork/Body/WeaponController.cs)：使用 Instantiate 发箭。尚未证明箭密度下实例化造成可见卡顿。
- [EncounterScope.ResetAll](../../Assets/Scripts/Combat/EncounterScope.cs)：遍历已注册对象并执行复位。接口契约存在，不代表所有实现的重复调用和顺序无关性已被运行验证。

“有分配入口”“成为性能瓶颈”“优化后更快”是三种不同结论，分别需要源码、采样与同条件对照。

## 2. 建立基线

1. 记录代码版本及未提交改动、Unity 版本、CPU/GPU、内存、操作系统、构建后端、分辨率、画质、VSync 与目标帧率设置。
2. 使用目标设备的 Development Build 连接 Profiler。Editor 可用于定位，但不要把 Editor 帧率作为玩家构建性能。
3. 先热身 30 秒，再各采样约 60 秒：原地/移动、连续近战、射箭、回生/复战。随机 AI 场景记录招式与攻击次数，避免把不同战斗负载直接比较。
4. CPU Timeline 看尖峰发生位置，Hierarchy 看调用次数、耗时及 GC Alloc；需要定位分配时启用 Allocation Call Stacks。Deep Profile 默认关闭，诊断后关闭再做对照，避免额外开销污染结论。
5. 保存原始采样，记录帧时间中位数、P95、最大值、GC 分配及关键方法耗时。P95 需从采样帧数据计算：排序后取覆盖约 95% 样本的位置，说明统计口径，不能从平均 FPS 推算。
6. 至少重复三轮。若波动大于改动收益，结论写“证据不足”，继续控制场景负载和采样条件。

CPU Profiler 支持分配调用栈，`GC.Alloc` 与 `GC.Collect` 也应区分；Deep Profiling 本身可能增加较高开销。参见 [Unity CPU Profiler](https://docs.unity3d.com/2022.3/Documentation/Manual/ProfilerCPU.html)。构建采样方法参见 [Unity：Profiling your application](https://docs.unity3d.com/2022.2/Documentation/Manual/profiler-profiling-applications.html)（该操作概览为 2022.2，界面以项目 2022.3 为准）。

## 3. 实验 A：命令分配来自哪里？

**假设**：持续移动的接口转换产生稳定分配；离散攻击只在输入触发时增加。假设需在目标后端确认。

**操作**：分别采集正常输入开放后的站立、持续移动和连续点击攻击；打开 GC.Alloc 调用栈，定位 `PlayerBrain.Update` 与 `BufferCommand` 入口。站立也可能发送零移动，不能用“没按键”假设没有命令。

**判断**：能指认分配的实际栈和频率才算验证。未出现样本时，检查是否打开调用栈、采样是否覆盖该路径、构建后端及优化差异。

**后续优化设计**：只改高频移动的传递方式，再重复同条件采样。除分配外，还要验证移动、垫步方向、受击后恢复和暂停。只减分配但破坏输入语义不算成功。

## 4. 实验 B：NonAlloc 是否漏结果？

**假设**：密集碰撞体可能填满现有 16 项 Overlap 缓冲；更多碰撞体不一定等于更多角色。

**操作**：使用临时场景副本，在同一查询体积内摆放 15、16、17 个符合 LayerMask 的碰撞体，记录查询返回数量及实际命中目标。这里是压力练习，不是当前单 Boss 场景的已知故障。

**判断**：返回数等于容量只能提示“可能饱和”，不能证明恰好只有这么多结果。对照一次更大缓冲或完整结果查询，核查丢失对象。检查代码是否有容量预警或回退。

**后续优化设计**：比较扩大预分配容量、检测饱和后扩容重试、减少查询层范围。记录高水位；不能只换成 NonAlloc 然后宣布“零 GC 且无漏检”。

## 5. 实验 C：一次攻击为什么没掉血？

按顺序收集证据，不要同时调整伤害、半径和时间窗。

1. 输入：是否触发普通攻击松手回调？门禁是否开放？命令是否被覆盖？
2. 状态：命令由哪个父/叶子处理，返回值是什么，是否进入攻击？
3. 时间：动画名与播放秒数是否匹配配置，当前脉冲是否有效？
4. 空间：Hitbox 是否开启，刀柄/刀尖挂点及 LayerMask 是否正确，查询命中了哪个 Collider？
5. 上报：是否被同目标去重，能否解析 Hurtbox.Owner，是否到达 ReportHit？
6. 响应：目标当前是普通受击、格挡、弹反、闪避还是处决保护？未扣血不一定是漏判。
7. 表现：真实 HP 变化后 UI 是否收到事件、绑定是否正确？不要把 UI 滞后当作没结算。

预期产物：一个复现步骤、一条中断在具体环节的链路、一次只改变单个因素的对照。诊断日志控制采样量，并在性能采样时关闭。

## 6. 实验 D：复战、暂停与重入

在场景副本或可恢复的演示环境中操作：

- 连续两次触发复战：检查血量、架势、输入、AI、UI 和投射物；第二次不应重复叠加初始资源或卡住。
- 射箭后复战：检查旧箭是否继续伤害新一局角色。
- 顿帧期间打开暂停再关闭：检查时间缩放最终是否恢复正确，UI 是否仍能操作。
- 忍杀/回生过程中复战：检查双方演出锁、朝向、无敌及输入门禁是否残留。
- 销毁一个已注册对象后复位：检查 `IsGone` 是否移除失效引用，而不是访问已销毁组件。

这些是验收目标，不是本轮已通过结果。失败后先定位哪个对象保留了旧状态，再判断是自身清理遗漏、顺序依赖，还是重复订阅。
