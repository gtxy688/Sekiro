# 事件总线与战斗表现：从逻辑事实到反馈

这一篇回答：战斗逻辑如何驱动 UI、音效、特效、相机和顿帧，又不直接依赖它们。

## 1. 基本方向

```text
战斗逻辑发布“发生了什么”
→ CombatEventBus
→ 表现模块决定“怎样呈现”
```

例如 `CombatStats` 只发布生命变化，不直接寻找血条；`DeflectState` 或结算层只发布弹反结果，不直接播放每一种音效和特效。

## 2. 主要事件类别

- 数值：HP、架势、命数、葫芦。
- 战斗：受击、格挡、弹反、拼刀、危字。
- 演出：忍杀开始/结束、投技、回生、死亡、胜利。
- 攻击：挥刀开始/结束、出箭。
- 相机与时间：震屏、特殊镜头、顿帧请求。

事件参数应携带表现需要的上下文，例如角色、命中点、弹反类型和危字类型，而不是让订阅者再回头猜全局状态。

## 3. UI

`CombatUIController` 订阅生命、架势、崩解、忍杀机会、葫芦和回生等事件：

- 玩家和 Boss 的血条分别更新。
- 架势条显示当前比例。
- Boss 崩解时锁定点切换成忍杀提示。
- 危字和喝药提示跟随角色。
- 回生时显示选择界面。

UI 需要明确绑定当前玩家和 Boss。未来切换 Encounter 时，应重新绑定目标，不能只依赖第一次场景引用。

## 4. 音效与特效

AudioManager 和战斗特效模块根据事件播放：

- 普通命中。
- 格挡和完美弹反。
- 武器拼刀。
- 危字、出箭和受击。
- 忍杀、死亡与胜利。

位置相关特效使用命中点或双方武器之间的计算点，避免所有火花都生成在角色根节点。

## 5. 相机与顿帧

相机系统订阅震屏、跳跃突刺和忍杀等事件。命中顿帧由 `TimeScaleController` 统一拥有修改 `Time.timeScale` 的权力，`CombatManager` 只申报 HitStop。

这避免多个系统同时保存和恢复 timeScale，造成暂停、慢动作和顿帧互相覆盖。

## 6. 为什么不直接调用

如果 `CombatStats` 直接调用 UI、Audio 和 Camera：

- 纯战斗逻辑无法独立复用。
- 新增一种表现需要修改结算代码。
- 没有 UI 的测试或场景也必须装配 UI 对象。
- 模块之间形成双向依赖。

事件总线把依赖方向固定为“表现依赖战斗事件”，而不是“战斗依赖所有表现组件”。

## 7. 静态事件的代价

`CombatEventBus` 是静态入口，使用方便，但存在：

- 订阅后忘记取消导致对象泄漏或重复响应。
- 事件来源不如直接调用容易追踪。
- 新订阅者可能无意中引入隐式行为。
- 事件不会自动回放当前状态，新 UI 绑定时仍需主动初始化。

订阅和退订必须成对放在合适的 Unity 生命周期中；跨场景对象尤其需要谨慎。

## 8. 面试回答

> 战斗逻辑只发布生命变化、弹反、忍杀等事实，UI、音频、相机和特效各自订阅。这样表现模块可以独立替换，结算层不依赖具体展示。静态事件总线的代价是调用链隐式和生命周期管理，因此订阅退订必须成对，并避免用事件代替所有直接调用。

## 面试追问梯度

### 基础概念

1. C# event、delegate 和直接方法调用有什么区别？
2. 事件发布者为什么不需要知道订阅者？

### 项目实现

3. 一次弹反如何同时驱动火花、音效、震屏和顿帧？
4. UI 如何区分事件中的角色是玩家还是 Boss？
5. 为什么 TimeScaleController 独占修改 timeScale 的权力？

### 方案取舍

6. 哪些通知适合走全局事件，哪些应使用直接调用？
7. 静态事件总线相比实例化 Signal/MessageBus 有什么代价？
8. OnEnable/OnDisable 与 Awake/OnDestroy 订阅各有什么风险？

### 扩展设计

9. 如果同时存在多场战斗或多玩家，静态全局总线怎样隔离作用域？
10. 如果需要事件回放或新 UI 立即显示当前状态，应增加什么机制？

### 故障排查

11. 血量已经变化但 UI 不更新，如何区分没发布、没订阅、绑定错对象和对象已销毁？
12. 一个音效播放两次，为什么首先怀疑重复订阅？

回答事件总线时必须同时说出解耦收益和隐式依赖、生命周期、作用域三个成本。
