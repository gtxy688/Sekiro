# 项目边界、架构代价与面试表达：最终复盘

这一篇不再介绍新功能，而是准备面试中的取舍题。

## 1. 项目最准确的定位

这是围绕弦一郎 Boss 战制作的个人战斗系统 Demo，不是完整商业游戏，也不是对《只狼》全部系统的复刻。

实现重点包括：

- 玩家与 Boss 的行为执行框架。
- 行为树动态选招。
- 格挡、弹反、闪避、识破、架势崩解和忍杀。
- 连续武器扫描与统一命中结算。
- ScriptableObject 数据和攻击时间轴工具。
- UI、音频、相机、顿帧、回生和复战重置。

## 2. 不应夸大的地方

- Command 是类型化意图消息，不是带 Execute/Undo 的完整 GoF Command。
- Boss 有多条命，但当前没有按 `LivesRemaining` 切换完整第二阶段招式池。
- 自研行为树规模较轻，没有成熟插件级可视化编辑器。
- 单槽输入缓冲不是完整命令队列。
- 当前自动化测试缺失，主要依靠 Unity 手动验收和静态配置校验。
- F8 是复战契约的调试入口，不是正式游戏流程。

## 3. 当前架构的真实代价

### CharacterBody 仍然较重

它是角色能力门面，虽然部分职责已经拆到 `CombatStats`、`WeaponController`、`FacingController` 和 `Locomotion`，仍然承担大量跨模块接口。

面试时可以说：当前优先保证 Demo 的统一角色入口；继续扩展角色类型时，会进一步按移动、战斗数值、武器与演出协调拆分。

### HFSM 调用链更深

父状态和叶子状态让公共规则集中，但增加调试难度，也容易出现顶层查询叶子状态的错误。项目通过语义化 API 和状态路径日志补偿。

### 事件总线是隐式依赖

表现解耦更容易，但订阅生命周期和事件追踪成本更高。它适合跨模块广播，不应该替代所有局部直接调用。

### 数据驱动增加配置风险

SO 和字符串动画名提高调参效率，也把部分错误从编译期推迟到配置期，因此需要时间轴工具和构建前校验。

## 4. 为什么没有自动化测试

当前项目主要验证动画、根运动、判定窗口和打击感，这些高度依赖 Unity 场景与人工观察，因此采用手动验收。

这不代表逻辑不能测试。下一步优先补 EditMode 测试：

- BossMovePicker 的距离、冷却和权重过滤。
- CombatStats 的生命、架势、崩解、命数和回生。
- AttackWindowSync 与配置校验规则。
- 输入缓冲的消费和超时语义。

再用少量 PlayMode 测试验证状态初始化、命令切换和核心场景装配。手感仍保留人工验收。

## 5. 如何回答 AI 辅助开发

应诚实区分代码产出与个人能力：

下面是表达模板，只保留自己实际做过、能展示证据的职责；仓库里存在代码不能证明个人贡献。

> 项目大量代码由 AI 辅助生成，我负责需求拆分、方案取舍、资源与场景装配、运行验收，以及发现问题后沿调用链定位和修改。为了确保自己能解释，我按简历中的每个技术点重新通读真实调用链，并能说明为什么采用、有哪些代价、下一步怎样改进。

不要声称每一行都是手写，也不能只说“AI 写的但我会用”。面试官真正判断的是你能否解释、验证和维护。

每条简历亮点配一份证据：需求或问题记录、本人做出的选择、源码入口、验证结果。没有记录的历史问题可以写成“现在的排查练习”，不要编成亲历事故。没有 Profiler 对照数据时，不写“零 GC”“帧率提升 X%”“支持百人同屏”。

可裁剪的技术描述：围绕单 Boss 战构建玩家与 AI 共享的角色执行层，以类型化命令和 HFSM 管理动作，用行为树组织 Boss 决策；使用配置化攻击窗口与 Cast/Overlap 判定，配套 SO 招式配置和攻击时间轴工具。描述中的“负责”“设计”“实现”需按真实参与程度分别填写。

## 6. 两分钟介绍结构

1. 项目目标：复刻弦一郎 Boss 战的核心交互。
2. 战斗循环：玩家输入和 Boss AI 通过共同执行层交战。
3. 一个技术重点：连续命中扫描与状态化命中响应。
4. 一个架构重点：行为树决策、HFSM 执行、Command 解耦来源。
5. 一个工程重点：SO 配置、时间轴工具和构建校验。
6. 诚实边界：个人 Demo、自动化测试不足、下一步改进方向。

## 7. 复习完成标准

你不需要背下所有类。应做到：

- 能从演示视频任意现象定位到对应系统。
- 能画出一次攻击和一次忍杀的调用链。
- 能说出每个架构选择至少一个收益和一个代价。
- 能明确区分当前已经实现的能力与未来可以扩展的能力。

## 面试官可能从简历怎样追问

### 从“Command + HFSM”开始

1. 这是真正的 Command 模式吗？
2. 为什么不用 Animator Controller 自己的状态机？
3. 玩家和 Boss 到底复用了哪些代码？
4. 输入缓冲为什么不是队列？

### 从“自研行为树”开始

5. 为什么不使用插件？
6. Selector 的 Running 怎样恢复？
7. 权重随机怎样保证不会选到冷却招式？
8. 当前两条命为什么不是完整二阶段？

### 从“连续扫描命中”开始

9. SphereCast 为什么仍然会漏？
10. OverlapCapsule 的刀柄与刀尖从哪里取得？
11. 如何去重，如何支持多段命中？
12. 如果性能不够，先优化哪一部分？

### 从“ScriptableObject + Editor 工具”开始

13. SO 运行时修改会怎样？
14. EditorWindow、CustomEditor 和 SerializedObject 分别是什么？
15. 修改资产怎样支持 Undo 和持久化？
16. 构建前怎样自动阻止坏配置？

### 从“事件总线”开始

17. 静态事件会不会内存泄漏？
18. 为什么不用直接调用？
19. 多场战斗如何避免全局事件串场？

### 从“AI 写代码”开始

20. 你亲自做了哪些决策？
21. 遇到过什么 AI 过度设计并怎样清理？
22. 如何证明自己能维护这份代码？

练习方式不是背答案，而是每题按四步回答：

```text
先给结论
→ 描述项目中的真实实现
→ 说明为什么这样选
→ 主动给出边界和下一步
```

## 自测

4. AI 写了大量代码时，你凭什么证明自己真正掌握了项目？
