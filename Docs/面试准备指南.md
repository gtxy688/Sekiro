# 面试准备指南 — 只狼弦一郎 Boss 战复刻

用 Unity 2022 LTS 复刻《只狼》苇名弦一郎 Boss 战的作品集项目，

核心难点是"打铁"手感的三个技术支点：

第一，命中判定不用 OnTrigger，改在 LateUpdate 里用 SphereCast 扫描
武器上一帧到当前帧的位移段，再叠一层 OverlapCapsule 覆盖刀柄到刀尖，
解决高速挥砍穿透和贴身刮过的漏检；

第二，角色逻辑用两层 HFSM 驱动，命令（Command）和受击（HitData）走
两条对称的自顶向下路由链，返回 bool 表示"是否拦截"，
这样"我当前在弹反吗/无敌帧吗"不需要任何状态类型判断；

第三，数值全部 ScriptableObject 化，表现层通过静态事件总线订阅，
UI/相机/音效零轮询。

Boss 是行为树 + 招式表驱动的，含交锋层、喝药惩罚层、主动抽招层三层，
并且复刻了只狼的"被动防御"——Boss 的格挡不是 AI 按键，而是玩家命中瞬间
的防御判定，会按计数升级为完美弹反并立刻反击。
```

## 第一梯队：必答，答不出基本出局

### Q1. 命中判定为什么不用 OnTrigger？

这是全项目最容易被追问、也最值得讲的一题。按这四层递进答：

| 层 | 问题 | 你的解法 |
|---|---|---|
| 1 | 高速穿透 | 刀在两帧间位移可能整个跨过目标，`OnTrigger` 只在离散帧检测 → 漏判。改成 `SphereCastAll(lastCastPos, radius, dir, distance)` 扫**线段** |
| 2 | 时序错位 | 动画在 `Update` 写骨骼，物理在 `FixedUpdate` 步进。直接在 `Update` 扫会读到上一帧的碰撞体位姿 → 在 `LateUpdate` 里先 `Physics.SyncTransforms()` 再扫 |
| 3 | 起点在碰撞体内部 | `SphereCast` 从碰撞体内部出发**不返回自身**，连招第二刀时刀常还叠在目标里 → 每帧再补一次 `OverlapSphereNonAlloc` 点检 |
| 4 | 贴身刮过 | 贴身站在挥砍内侧时刀尖从身侧划过，只扫刀尖会漏 → 额外叠 `OverlapCapsuleNonAlloc(hilt → tip, shaftRadius)`，把柄到尖整段盖上 |

**追问：一次挥砍会不会对同一目标重复结算？**
三个 HashSet 各司其职，讲清楚它们的区别是加分项：

- `hitTargets` — 本次判定期内命中过的目标，防止一刀多次结算
- `blockedUntilExit` — **开判定那一刻就已经叠在刀上的目标**，先不算，等它离开再重新扫进来才算新的一刀。这是连招第二刀能生效的关键
- `clashedPartners` — 拼刀去重

**追问：双方 Hitbox 相交，拼刀会不会双倍结算？**
会。所以 `TryClash` 里有一行断言式去重：

```csharp
if (GetInstanceID() > other.GetInstanceID()) return;
```

只让 InstanceID 较小的一方上报 `CombatManager.ReportClash`。这个技巧可以顺带讲"确定性 tie-break"的思路。

**追问：动画 Clip 上残留的 Enable 事件怎么办？**
`Hitbox.Enable()` 入口有 `AttackWindowSync.CanMeleeHit(HitStartTime, RecoveryWindowStart, hitPulses)` 闸门，弓段和 0.01s 假窗就算 Clip 上留了事件也扫不出刀。

> 文件：`Assets/Scripts/Combat/Hitbox.cs`

### Q2. 弹反（Deflect）是怎么做的？

这是项目的招牌。讲的时候抓住**三个反直觉的设计决策**：

**① 短按弹反 / 长按格挡，不是两套输入**
按下即进 `DeflectState`，窗口内挡住 → 完美弹反；窗口外挡住 → 普通格挡（扣少量血 + 涨架势）。松手行为区分长按/短按。

**② 抖刀惩罚（防无脑连点）**
`Config.DeflectMashWindow` 内的重复举刀会置 `raiseSpamGuard = true`，**即使在弹反窗口内也只算普通格挡**。这个机制直接复刻只狼的"连点防御会被打穿"。

**③ 完美弹反时自己的架势永不崩**
`AccumulatePosture(..., allowBreak: false)` —— 只狼的核心承诺：你弹得准就绝对不会因为弹反而崩防。

**追问：弹反后 Boss 立刻反击，怎么保证"贪刀必被罚"？**

这是整个项目最精妙的一处，一定要讲：

```csharp
// 反击的发起时刻按 "目标命中时刻 - 该招 HitStartTime" 倒推
counterFireTime = 目标硬直结束 + ParryCounterHitDelay - 反击招.HitStartTime;
```

`BT_Kengeki` 在弹反瞬间就把反击招抽好存进 `pendingCounter`，到点直接切入。因为玩家恢复后想出刀有约 0.15s 前摇，**玩家的刀永远晚于反击命中**——这是数学上保证的，不是调参调出来的。

**追问：Boss 也会格挡/弹反玩家吗？怎么实现的？**

关键认知：**Boss 的防御不是"AI 按防御键"**，而是玩家命中瞬间在 `CharacterBody.TryPassiveDeflect` 里做的一次防御判定，分两种结果：

- `DeflectEntryMode.PassiveGuard` — 普通格挡，留下防御姿态
- `DeflectEntryMode.PerfectParry` — 计数达到阈值后升级为完美弹反，弹开玩家

这是从"AI 模拟输入"到"命中即判定"的建模转变，讲出来很显功力。

> 文件：`Assets/Scripts/FrameWork/States/Ground/DeflectState.cs`（688 行）

### Q3. 为什么用 HFSM？命令和受击怎么路由？

**结构**：顶层只装 `HierarchicalState`（`GroundedState` / `AirState` / `StunnedState`），叶子状态永远在父状态的 `SubStateMachine` 里。

**两条对称路由链**：

```
Command(输入/AI)  → HandleCommand(cmd)   → 父拦截? → 子状态
HitData(物理碰撞) → OnHitReceived(hit)   → 父拦截? → 子状态
返回 true = 拦截，停止传递（Command 还会清空缓冲池）
```

**为什么要镜像？** 因为"受击结算需要知道当前在弹反吗/无敌帧吗/硬直中吗"，而这套信息天然分布在状态树里。用一条和命令完全对称的路由链，就把"查询当前状态"变成了"沿着树问一圈"。

**项目里的硬约束（必须能背出来）**：

> 禁止在业务代码里判顶层状态类型。`MainStateMachine.CurrentState is DodgeState` 永远为 false。

**怎么绕过的？** 在 `CharacterBody` 上暴露语义化 bool 属性作为唯一的跨层查询接口：

```csharp
IsAttacking / IsParried / IsGuarding / IsGuarding / IsPostureBroken / IsFinisherLocked
```

以及封装 API：`IsGroundedTop` / `IsInGroundedSubState<T>` / `TryChangeGroundedSubState` / `ForceChangeGroundedSubState`。

**为什么这条约束值得讲**：类型判断是编译期耦合，一旦有人往顶层插一层状态机，所有 `is XXXState` 全静默失效。用 bool 属性把"状态身份"降级成"数据快照"，加层不影响任何调用方。

> 文件：`Assets/Scripts/FrameWork/States/Base/BaseState.cs`、`HierarchicalState.cs`

## 第二梯队：高频，答好拉开差距

### Q4. 架势（Posture）系统的数值设计

三条公式，要能写出来：

```csharp
// 1. 自然回复（延迟后）
rate = Config.PostureDecayRate;
if (IsGuarding) rate *= Config.GuardPostureRecoveryMultiplier;  // 格挡姿态 ×5

// 2. Boss 非线性：架势越高回越慢（反函数手感）
if (Config.PostureDecayInverse)
    rate *= 1f - CurrentPosture / Config.MaxPosture;

// 3. 应用
CurrentPosture = Mathf.Max(0f, CurrentPosture - rate * Time.deltaTime);
```

**为什么非线性？** 线性回复下 Boss 残血架势反而回得快，玩家永远打不崩。改成反比例后，"高架势"状态有黏性，营造只狼那种"压着打就能崩防"的正反馈。

**追问：崩解来源为什么要记录？**
`PostureBreakSource` 有三个值 `Attack / Deflect / Mikiri`，对应三种处决演出：

```
PostureBreakSource.Attack   → FinisherKind.Ground  → "Finsher_Ground"
PostureBreakSource.Deflect  → FinisherKind.Deflect → "Finsher_Deflect"
PostureBreakSource.Mikiri   → FinisherKind.Mikiri  → "Finsher_Mikiri" / "Finsher_Miriki"
```

`CombatManager.TryExecuteAvailableFinisher` 会根据崩解来源自动选对应演出。注意代码里还兼容了 `Miriki`/`Mikiri` 两种拼写（解包资源命名不一致），这种细节说出来很真实。

### Q5. Boss AI 的树长什么样？

一个 `Selector` 挂 5 个节点，优先级从上到下：

| 顺序 | 节点 | 职责 |
|---|---|---|
| 1 | `ConditionNode` | 崩解 / 忍杀锁定 / 被弹反硬直 → 返回 Success 吃掉本帧，不落到走位 |
| 2 | `BT_Kengeki` | **交锋层**：被弹反/硬直结束后的反击 |
| 3 | `BT_HealPunish` | **喝药惩罚层**：抓玩家喝葫芦，改用重箭 |
| 4 | `BT_PickActive` | **主动抽招层**：按权重 + 冷却从招式表抽招，带出招后强制走位间隔 |
| 5 | `BT_MoveToTarget` | 追击走位（绕圈 + 逼近分量分离） |

**追问：招式怎么组织的？**
`GenichiroMoveCatalog` + `BossMoveTable`（SO）。每条 `BossMoveEntry` 含 id、冷却、权重、多个动画序列（`BossAnimSequence`）、每个窗口的伤害覆盖（`BossMoveWindow`）。运行时由 `BossAttackBaker.Bake(entry, anim, window)` 现场烘焙成 `AttackConfig` 挂到 `body.ActiveAttack`。

> 讲"烘焙"这个词：招式表是静态数据，运行时按当前段和窗口生成一份 AttackConfig，避免为每招每段手工建 SO 资产。

**追问：连招段与段之间怎么切？**
`BT_ExecuteMove.FireCurrentSegment` 里有个坑值得主动提：

```csharp
// 第二段起直接切 AttackState，避免先进 Idle 再 CrossFade
// 导致跨子状态机读不到动画时间
bool startedMove = segment > 0
    && body.TryChangeGroundedSubState(g => new AttackState(body, g, baked));
```

### Q6. 数据驱动与表现层解耦

- 数值全 SO：`CharacterConfig`（血量/架势/移动/葫芦/复活）+ `AttackConfig`（伤害/架势伤害/判定窗/连招派生/危字标记/出伤脉冲/音效 cue/出箭 cue），都带 `[CreateAssetMenu]`
- 命令与 Hit 数据用 **struct**（值类型，避免引用语义）
- 状态是**纯 C# 类**（非 MonoBehaviour），只有 `CharacterBody` 是 MonoBehaviour —— 这点要主动讲，说明你理解 MonoBehaviour 的开销
- `CombatEventBus` 静态事件总线，20+ 事件；表现层（UI/相机/音效）只订阅，零轮询

**为什么这条重要**：`CombatEventBus.TriggerPostureChanged` 这种推送让 UI 完全不需要 `Update` 里读 `CharacterBody.CurrentPosture`。

## ⚠️ 最大风险点：AI 辅助开发怎么说

`CLAUDE.md` 第 54 行白纸黑字写着：

> **AI 辅助开发，用户负责测试与验收（按模块）**。AI 每完成一个模块，交付「验收清单」供用户逐条验证，验收通过才算完成。

**秋招面试官 100% 会问："这个项目哪些是你写的？"**

### 推荐的应答框架（诚实 + 有力）

> "我用 AI 作为结对编程工具，但架构决策和验收标准是我定的。具体来说：
>
> **我负责的部分**：
> - 整体架构分层和那几条硬约束——比如'禁止判顶层状态类型'、'命中判定不用 OnTrigger'、'伤害数值只归 AttackConfig'，这些是先定的规矩，再让 AI 在这个框里实现
> - 只狼的战斗机制拆解——弹反窗口、抖刀惩罚、架势非线性回复这些数值和手感设计是我自己反推和调的
> - 全部验收——`Docs/验收清单.md` 里每一条都是我在 Unity 里手动跑出来的
>
> **AI 负责的部分**：大量样板代码、模块实现、文档整理。
>
> **我能证明我懂的方式**：你可以挑任何一个模块问我'为什么这么设计'和'哪里有问题'——我知道 `CharacterBody` 是 God Class、知道 `Blackboard` 有装箱、知道状态机每次 new 会产生 GC，这些我都能讲清成因和改法。"

### 为什么这个说法站得住

因为**你确实做了最难的部分**：架构约束、机制反推、验收。这三者恰恰是初级工程师最缺的。而且——**能指出自己代码问题的人，比写出"完美"代码的人更可信**。

### 一个反向加分技巧

主动把 `CLAUDE.md` 里那几条硬约束讲出来。这不只是辩解，它在证明：

> "我在用 AI 之前，先把架构约束写死成文档，让 AI 在约束内实现——这本身就是工程能力。"
