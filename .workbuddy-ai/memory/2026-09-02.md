## 12:00 UI 真相调查（靠写脚本解析场景，别再 grep 猜）

小金问「UI 怎么实现的、为什么运行后才显示、Controller 为什么这么多代码」。
**我连续两次判断错误**，最后写脚本解析场景文件才查实。

### 真实情况（证据确凿）

`GameScene.unity` 共 **186 个物体，全部是根物体，没有一个有子物体**——
**UI 层级在场景里是"拍平"的，父子关系全丢了。**

- `CombatCanvas` 子物体 **0**（GameObject 块里连 `m_Children` 字段都没有，Unity 会省略空列表）
- `GamePanel` / `SettingPanel` / `RootPanel` / `HubPanel` / `SettingsPanel` / `RespawnPanel` / `EndPanel` → **全是根物体，全是空壳**
- 大量重复残留：「继续战斗」×2、「设置」×3、「返回」×4、「键位设置」×3、
  `Fill Area` ×4、`Dimmer` ×2、`Dot0` ×3、12 个「—」占位

**运行时必然走的路径**：

```
FindCombatCanvas()           → 找到 CombatCanvas（空的）
canvas.Find("SettingPanel")  → 失败（SettingPanel 在根层，不是子物体）→ new 一个新的
TryBindExisting()            → 在新 panel 下找 RootPanel/按钮 → 全找不到 → false
BuildUIInto()                → 用代码把整棵树拼出来
```

**暂停菜单 100% 运行时生成**，每次进游戏重新拼一遍；场景里那些散落物体是历史残留。

### `PauseMenuController` 为什么 1450 行 / 91 个方法

它**用代码手工拼整个 UI 层级**：`CreateMenuButton` `CreateSliderRow` `CreateRebindRow`
`CreateImage` `CreateLabel`，每个元素手动设 anchor / sizeDelta / 颜色 / 字体 / onClick。
UI 脚本共 4085 行，它一个占 35%。
**不是设计差，是被迫的**——层级没预装只能用代码拼。预装的话 Controller 只要 200~300 行。

### 🔴 我的两次错误判断

1. **第一次**说"UI 全是提前装好的"——错。血条是预装的（`[SerializeField]` 拖引用，
   不依赖层级），但**暂停菜单是运行时生成的**。我用血条的情况盖过了暂停菜单。
2. **第二次**说"场景里按钮一处都没有，所以必然走生成"——**结论碰巧对，证据是错的**。
   按钮**在**场景里（各 2~4 份），只是 Unity 把中文名存成 Unicode 转义
   （`\u7EE7\u7EED\u6218\u6597` = 继续战斗），**我 grep 中文明文当然 0 处**。

### 技术教训

- **grep Unity 场景/资源文件查中文，要处理 `\uXXXX` 转义**，否则查什么都是 0，然后得出错误结论。
- **判断"预装 vs 运行时生成"不能只读代码**——fallback 走不走取决于场景层级。
  写脚本解析场景才是硬证据（`Temp/scene_tree.py` 打印子树、`Temp/parent_of.py` 反查父链）。
- `Transform.Find()` 只找**直接子物体**，父挂错一层就等于找不到，**且不报错**——静默走 fallback。
