## ⚠️ 「UI 是 MVC」这个说法不准确，实际是 MVP 的 Passive View

小金问「我们这是 MVC 吗？为什么没看到 M」。查证结论：

**M 是存在的，只是不在 UI 目录**：`CharacterBody`（`FrameWork/Body/`，运行时状态
`CurrentHP`/`CurrentPosture`/`GourdRemaining`/`LivesRemaining`）+ `CharacterConfig`（`SO/`，ScriptableObject，
静态配置 `MaxHP`/`MaxPosture`/`LifeCount`/`ReviveCount`）。两者合起来就是 Model。

**但严格说这不是经典 MVC，而是 MVP 的 Passive View。** 判据很硬：

```csharp
// CombatUIController.HandleHPChanged
float ratio = maxHp > 0 ? (float)currentHp / maxHp : 0f;   // Controller 做格式化 + 除零保护
playerStatusView?.SetHP(ratio);                            // View 只收 0~1 的比例
```

View 连「最大血量是多少」都不知道，只收已经算好的显示值——这是 Presenter 的活。
经典 MVC 里 View 直接观察 Model，这里的 View 什么都不订阅、不轮询、不读 Model。

**证据链**：
- 事件签名 `Action<CharacterBody, int, int>` 里 `CharacterBody` **只用于身份比对**（`c == playerBody`），
  数值走的是值快照参数。`CombatEventBus.cs:29` 注释写明「表现层不读 CharacterBody 内部字段」。
- 唯一反向操作 Model 的地方：`HandleReviveChoiceReady` 把 `playerBody.TryExecuteCommand(...)` 包成 lambda 交给 View，
  用户点击时执行——这是标准的 Presenter 手法（View 不认识 Model，只持有回调）。

**文档口径不一致（待小金裁定，不自行改）**：`Docs/策划案.md`、`Docs/total.md:102`、`Docs/实现指导.md:146`、
`Docs/项目总结与回顾.md:146`、`Docs/面试准备-苇名之刃.md:426` 全部写「MVC」。
面试稿里写 MVC 会被追问「你的 Model 是什么」，建议改成更准确的说法，但改不改由他定。

**架构上真实存在的一处不纯**：`CombatUIController.Start()`（114-121 行）与 `ResetForEncounter()`（194-200 行）
**直接读 Model**（`c.CurrentHP`、`c.CurrentPosture`、`playerBody.GourdRemaining`）。
原因合理——`InitCombat` 不发事件，不读一次开局血条是空的。但这是裂缝：
更干净的做法是让 `InitCombat` 也发一次事件，Controller 就完全不必认识 Model 的字段。
（`ResetForEncounter` 里读的是 `Config` 而非 body 当前值，是**在裂缝中选了安全的一侧**：
Config 是序列化 SO 整局不变，读它没有复位顺序依赖；body 可能读到未复位的残值。）
