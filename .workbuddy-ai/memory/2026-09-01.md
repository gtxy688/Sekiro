**结论**：CombatManager 431 行确实病了，但病灶是「成对演出编排」，不是「同时处理 player 和 boss」。

**发现的文档/代码冲突（未解决，已报告用户）**
- `Docs/architecture/03-hit-detection.md` 第 80-106 行：CombatManager 只定义为 ReportHit / ReportClash + 单例的**无状态中间层**。

**三个真问题**
1. `if (initiator != PlayerRef) return false;` —— 「只有玩家能处决」这条游戏规则被编码成对象身份比较，与 CLAUDE.md 第 5 条（数值走 SO）精神冲突；加第二个敌人即崩。

3. HitStop 改全局 `Time.timeScale`，且已与 GamePause 纠缠（`Time.timeScale = GamePause.IsPaused ? 0f : 1f`）→ 两个系统抢同一全局变量。

**批评过头的部分**
ReportHit / ReportClash 里 attacker / target 全部取自 hitbox/hurtbox.Owner，从不区分 player/boss —— 这部分是对的，正是中间层的价值所在（结算层不该知道谁是谁）。只有后半段 PlayerRef/BossRef 破坏了它。

**建议拆法（未实施，等用户确认）**
- `CombatResolver`：无状态，留 ReportHit/ReportProjectileHit/ReportClash，可不必是 MonoBehaviour。
- `DuelDirector`：有状态，但每次演出一个 `PairedPerformance` 实例对象，取代 8 个单例字段；处决/投技同为其实例。
- `HitStop` → 独立 TimeFx 服务，全局 timeScale 只留一个主人。
- `IgnoreCharacterPhysics` + `ArenaBoundary.Ensure()` → 独立 ArenaSetup，移出结算器。
- PlayerRef/BossRef → 改为「处决资格」查询（阵营/配置 SO 驱动），去掉对象身份比较。

**优先级建议（秋招时间表）**
必做：去 PlayerRef/BossRef 硬编码 + 抽 PairedPerformance 对象。
缓做：HitStop / ArenaSetup 搬家（风险低、收益低）。

## 能力盘点：三题校准结果（小金主动要求「拷打」，不要吹捧）

**⚠️ 我的失误**：第一版出题时把答案写在题干后面（及格线、陷阱都抖出来了）→ 小金要求撤答案，整批作废换新题。教训：**拷问不能给提示，给了就是开卷。**

**三题表现**
| 题 | 层次 | 结果 |
|---|------|------|
| 1. HFSM 顶层为何只装 HierarchicalState | 设计 | **不及格（答偏）**：答的是"受击/忍杀时不能闪避"这个**目的**，没答机制；且举例有误（受击期间**能**垫步，只是有窗口）；**漏掉 Hit 侧路由** |

| 3. 招式判定时间怎么定的 | 经验 | **这是真东西**：对着动画一帧帧调；踩过「把判定条缩成 0~0.01」的坑（进招第 0 帧 animTime=0，`0>=0 && 0<0.01` 亮刀一帧）并定位根因 |

## 修正：EncounterScope 改为自动兜底（`Ensure()`）——我又一次想复杂了

**触发**：小金按验收清单跑到 A 项，Console 弹出我埋的 `场景里没有 EncounterScope` 警告。查证：GUID 全工程零命中，确实没挂。

**但真正要记的是我上一轮的判断错误**：我否决"自动创建"的理由是「跨组件 Awake 顺序不定，CombatManager 里 AddComponent 可能造出第二个 Scope」——**这个理由是错的**。

> **Unity 生命周期保证：所有 Awake 全部跑完 → 才进 Start。**
> 所以在 `Start` 里判断 `Current == null`，就一定是场景里真没有，不可能误判、不可能重复创建。
> 我把一个「放 Start 就已被保证」的问题当成不确定来处理，凭空加了一道手工步骤。

**改法**（与项目既有的 `ArenaBoundary.Ensure()` 同一模式）：
1. `EncounterScope.Ensure()`：无则 `new GameObject("EncounterScope (Auto)")` + `AddComponent`，打一条 Log 说明。
2. `HasParticipants` 属性：区分「配好的 Scope」与「自动兜底的空壳」。
   `ValidateFinisherRefs()` 改判 `HasParticipants` 而非 `Current != null`——否则兜底会把「PlayerRef 忘了拖」这个配置错误一起吞掉，诊断变差。
3. **⚠️ 顺序陷阱（关键）**：不能只靠 CombatManager 先建好 Scope。**各组件的 Start 顺序同样不定**，若 `CharacterBody.Start()` 跑在 `CombatManager.Start()` 之前，它注册时 `Current` 仍是 null → 复位契约对 CharacterBody 照样失效。
   → **每个注册点都自己调 `Ensure()`**，谁先跑到谁负责创建，后跑的复用同一个。

**配套硬约束（已写进验收清单）**
- `Start()` 里用 `EncounterScope.Ensure()?.Register(this)` —— **用 Ensure，不写 `Current?.`**
- `OnDestroy()` 里用 `EncounterScope.Current?.Unregister(this)` —— **这里必须 Current，不能用 Ensure**（销毁时创建新对象毫无意义）
- `Ensure()` 只能在 Start 及之后调，**不可在 Awake 里调**

**验证**：6 个注册点全部改完（CombatManager 用局部变量 `scope?.Register`，等价）；6 个注销点全部保持 Current。

**方法论教训（第三次同类）**：遇到「顺序不确定」的担忧，先确认它落在生命周期哪一段。
- 放 `Awake` → 顺序确实不定，需要防御
- 放 `Start` → 所有 Awake 已跑完，跨组件初始化**是安全的**，不需要防御

这次和「倒序遍历保证顺序」是同一个误区的两面：一次**误以为有保证**（倒序），一次**误以为没保证**（Start 里的 Current）。
