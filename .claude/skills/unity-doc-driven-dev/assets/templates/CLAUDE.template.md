# 代码规范

## 命名
- 公开成员 PascalCase，私有 camelCase
- 命令 struct 命名 `<动作>Command`
- 状态类命名 `<区域><动作>State`

## 文件组织
- <目录约定，如：状态机 → `Assets/Scripts/FrameWork/States/`>
- <核心玩法 → `Assets/Scripts/Gameplay/`>
- <表现 → `Assets/Scripts/UI/`、`Assets/Scripts/Audio/`>

## 命名空间
- 全部代码位于 `<项目缩写>.*`，与文件夹结构对齐
- 跨模块引用一律 `using <命名空间>;`，禁止在全局命名空间新增类型

## 数据结构
- 配置数据用 ScriptableObject，带 `[CreateAssetMenu]`
- 命令/事件数据用 struct（值类型）
- 状态是纯 C# 类（非 MonoBehaviour）

## 注释
- 中文注释，解释"为什么"而非"是什么"
- 占位资源名注明「接资源前为占位名」

# 工作流（AI 实现 → 用户验收）

1. 收到任务 → 按「文档加载指引」读对应架构文档，只读需要的章节
2. 实现代码 → **不自己宣称"完成"**
3. （项目有自动化测试时）实现后先跑相关 EditMode/PlayMode 测试，全 PASS 才进入交付
4. 交付时附「验收清单」：操作步骤 + 预期结果（供用户在 Unity 中逐条验证），同时报告自动化测试结果
5. 用户验收通过 → 提交；不通过 → 修正后重新交付

# 文档访问纪律（硬规则）

1. 收到任务 → 在索引表定位对应架构文档，**只读该文件**，禁止通读 `Docs/` 下所有文档
2. 禁止跨模块引用其他文档
3. **动手前先声明**：先说出"本任务要读哪份文档"，再开始读取，让用户确认找对了文档
4. 文档与代码冲突 → **停下报告，不自行选边**
5. 遇到缺失的文档或字段 → 停下询问用户，**不臆造**

# 测试要求

<按项目测试策略二选一，删除另一方案>

## 方案 A：自动化测试 + 手动验收清单（推荐给数值/状态机密集项目）

- 新增数值逻辑 → 必须配套 EditMode 单元测试（`Assets/Tests/EditMode/`）
- 新增状态转换 → 必须配套 PlayMode 集成测试（`Assets/Tests/PlayMode/`）
- 修改已有逻辑前 → 先运行现有测试确保不回归
- 测试运行方式：Unity Editor → Window → General → Test Runner
- 自动化测试证明"逻辑对"，手动清单证明"手感对"：AI 交付「验收清单」（`Docs/architecture/0X-xxx-test.md`）+ 自动化测试结果，用户在 Unity 中逐条验证
- 深度场景测试用简化策略（装配无异常 + 关键事件触发），手感留给手动验收

## 方案 B：手动验收清单（轻量项目）

本项目不做自动化测试。AI 交付时附「验收清单」（`Docs/architecture/0X-xxx-test.md`），用户在 Unity 中手动逐条验收。`-test` 指手动验收清单，不是自动化测试，禁止据此编写测试代码或测试程序集。
