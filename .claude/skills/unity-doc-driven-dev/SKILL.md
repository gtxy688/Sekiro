# Unity 文档驱动开发

## 核心思想

**先定需求，再拆模块，分文档写设计**——让每个开发任务都能快速定位到所需的那一份模块设计文档。

三份文档分工明确，不可混用：

| 文档 | 回答 | 定位 |
|------|------|------|
| 需求/策划案文档 | 做什么、数值多少 | **唯一权威**，冲突时以它为准 |
| 架构文档 | 怎么实现、按什么顺序 | 不含代码，只写思路 |
| 验收文档 | 怎么验证做对了 | 自动化测试（EditMode/PlayMode）+ 操作步骤 + 预期结果 |

验证手段分两层，不可互相替代：
- **自动化测试**：覆盖可判定的逻辑——数值、状态转换。跑一遍即得"对/错"
- **手动验收清单**：覆盖手感与表现——操作步骤 + 可观察预期结果。自动化的边界在"手感"

## 何时使用

- 新建 Unity 项目，需要从零搭建文档体系
- 需求已定，需要拆模块并写各模块设计文档
- 按模块实现功能时，需要确定该读哪份文档
- 交付前生成验收清单
- 需要沉淀项目的架构红线与代码规范

## 文档体系

标准目录结构：

```
Docs/
├── <需求文档>.md              # 需求 + 数值，唯一权威
├── 实现指导.md                 # 实现思路总纲
├── progress.md                # 进度追踪
├── total.md                   # 用户决策记录（AI 不当规范用）
└── architecture/
    ├── 00-overview.md         # 模块清单 + 依赖图 + 文档索引表
    ├── 0X-xxx.md              # 模块架构文档
    └── 0X-xxx-test.md         # 模块验收文档（自动化测试 + 手动验收清单）
```

配套的自动化测试目录（有自动化测试的项目）：

```
Assets/Tests/
├── EditMode/                 # 单元测试：数值逻辑、纯 C# 逻辑，无需进 Play
└── PlayMode/                 # 集成测试：状态转换、场景装配、核心链路
```

用 `assets/templates/` 下模板生成，按项目裁剪。

## 工作流 A：新项目 / 新需求（搭建文档体系）

1. **定需求**：写需求文档（做什么 + 数值）。数值集中一处，避免散落各处。
2. **拆模块**：按依赖分层，编号 M1/M2/…，标出每层依赖关系。
3. **建总览**：写 `00-overview.md`——模块清单表 + 依赖图 + 文档索引表。
4. **定测试策略**：项目是否做自动化测试——做就定目录（`Assets/Tests/EditMode/` + `PlayMode/`）与覆盖边界（数值逻辑→EditMode 单测，状态转换/装配→PlayMode 集成测试；手感表现→手动验收），不做则只用手动验收清单。
5. **写约束**：把索引表 + 访问纪律 + 代码规范 + 测试策略写进项目 `CLAUDE.md`。
6. **逐模块展开**：需要实现哪个模块，才写哪个模块的架构文档 + 验收文档。**不要一次写完**，容易过时。

模块拆分原则见 `references/module-splitting.md`，
自动化测试分层与写法见 `references/automated-testing.md`。

## 工作流 B：日常开发任务（收到任务时）

1. **定位**：在项目索引表中按任务类型找到对应架构文档
2. **声明**：动手前先说出"本任务要读哪份文档"，让用户确认找对了
3. **只读该文档**：读到需要的章节即可，禁止通读 `Docs/` 全部文档
4. **实现**：遵循项目架构原则与代码规范；**修改已有逻辑前先跑现有测试防回归**（项目有自动化测试时）
5. **测试**：项目有自动化测试时——新增数值逻辑配套 EditMode 单测、状态转换配套 PlayMode 集成测试，Test Runner 全 PASS 后才算实现完成
6. **交付**：对照 `0X-xxx-test.md` 生成「验收清单」（操作步骤 + 预期结果）**并报告自动化测试结果**，**不自己宣称"完成"**
7. **验收**：自动化测试全 PASS + 用户在 Unity 中逐条验证；不通过则修正后重新交付

> 自动化测试与手动验收的分工：**自动化测试证明"逻辑对"，手动验收证明"手感对"**。两者互不替代——即使自动化全 PASS，手感类验收项仍需用户逐条确认。

## 文档访问纪律（硬规则）

1. 只读与当前任务相关的文档，**禁止通读 `Docs/` 下所有文档**
2. **禁止跨模块引用**文档（做哪个模块就读哪个模块的文档）
3. **动手前先声明**要读哪份文档，让用户确认找对了
4. 文档与代码冲突 → **停下报告，不自行选边**
5. 缺失的文档或字段 → **停下询问，不臆造**

深入说明与常见反模式见 `references/doc-discipline.md`。

## 文档索引表（核心机制）

索引表是让 AI 快速定位的关键，同时放在 `00-overview.md` 与项目 `CLAUDE.md` 中：

| 任务类型 | 读这个 |
|---------|--------|
| <任务关键词> | `Docs/architecture/0X-xxx.md` |
| 项目总览/模块依赖 | `Docs/architecture/00-overview.md` |
| 用户决策记录 | `Docs/total.md`（用户视角，AI 不当规范用） |

写法要点：
- 用**任务关键词**（开发者/用户会说的话）而非模块编号，降低匹配成本
- 一行一个模块，映射唯一文档，避免一对多
- 用户决策记录单独标注"AI 不当规范用"，防止把历史讨论当准则

## Unity 通用架构原则

适用于**所有游戏类型**（动作、卡牌、Roguelike、平台跳跃、模拟经营、解谜…）。项目有特殊约定时以项目文档为准：

1. **数据驱动**：配置与逻辑分离，数值走 ScriptableObject / 配置表，不硬编码在 .cs 里
2. **关注点分离**：逻辑层不直接依赖表现层，UI/音效/相机订阅事件，不每帧轮询
3. **状态可管**：复杂对象的行为用状态模式组织，避免巨型 switch 与布尔标志堆砌
4. **生命周期成对**：事件订阅、协程、对象池借还成对出现，避免泄漏
5. **性能基线**：缓存组件引用，避免 Update 中 Find/Linq/装箱，高频实例化走对象池

详解见 `references/unity-architecture-rules.md`。

## 代码规范

- 命名空间与文件夹结构对齐，不在全局命名空间新增类型
- 公开成员 PascalCase，私有 camelCase
- 配置数据用 ScriptableObject，短小的命令/事件数据用 struct
- 注释解释"为什么"而非"是什么"
- 占位资源名（动画/音效）注明占位状态

## 自动化测试（Unity Test Framework）

**原则：自动化测试是验收文档的一部分，不是替代品。** 两层各司其职：

| 层 | 放哪 | 测什么 | 典型写法 |
|----|------|--------|---------|
| EditMode 单测 | `Assets/Tests/EditMode/` | 数值、纯逻辑 | `ScriptableObject.CreateInstance<T>()` + NUnit `[Test]` + `Assert.*` |
| PlayMode 集成测试 | `Assets/Tests/PlayMode/` | 状态转换、场景装配、核心链路 | `[UnityTest]` + `IEnumerator` + `yield return null` |
| 手动验收清单 | `Docs/architecture/0X-xxx-test.md` | 手感、表现、边界操作 | 操作步骤 + 预期结果表 |

配套要求（写进项目 CLAUDE.md 的测试策略）：

- 新增数值逻辑 → 必须配套 EditMode 单元测试
- 新增状态转换 → 必须配套 PlayMode 集成测试
- 修改已有逻辑前 → 先运行现有测试确保不回归
- 测试运行方式：Unity Editor → Window → General → Test Runner
- 深度场景测试的**简化策略**：PlayMode 测「场景装配无异常 + 关键事件触发」，完整手感验证留给手动验收清单

测试命名：测试类 `<被测类>Test`（`PostureSystemTest`），测试方法 `<行为>_<预期>`（`TransitionTo_SwitchesState`）。
测试代码与实现代码同批交付，提交信息带 `test:` 前缀（`test: PostureSystem 单测`）。

详细写法、完整示例与反模式见 `references/automated-testing.md`。

不做自动化测试的项目：跳过本章，工作流回到纯手动验收清单即可，无需强加。

## 验收清单写法

每条 = 操作步骤 + 预期结果，供用户在 Unity 中逐条验证：

```
| # | 操作步骤 | 预期结果 | 通过 |
|---|---------|---------|------|
| 1 | 进入 Play，按 <键> | <可观察现象> | ☐ |
```

项目有自动化测试时，验收文档同时包含两层：**EditMode/PlayMode 测试用例表**（可自动判定）+ **手动验收清单**（手感/表现）。手动清单只保留自动化覆盖不到的部分，不重复列"数值对不对"这类已由单测证明的项。

## 模板

`assets/templates/` 提供可直接复制改造的文档模板：

| 模板 | 用途 |
|------|------|
| `design-doc.template.md` | 需求 + 数值（唯一权威） |
| `00-overview.template.md` | 模块清单 + 依赖图 + 索引表 |
| `module-architecture.template.md` | 单模块架构设计（不含代码） |
| `module-test.template.md` | 单模块验收文档（EditMode/PlayMode 测试用例 + 手动验收清单） |
| `CLAUDE.template.md` | 项目约束（索引表 + 纪律 + 规范 + 测试策略） |
| `progress.template.md` | 进度追踪 |

用法：复制模板到目标项目的 `Docs/` 相应位置，替换 `<占位符>` 并按项目裁剪。CLAUDE 模板产出物放在项目根目录，文件名依 AI 工具而定（`CLAUDE.md` / `AGENTS.md` 等）。
