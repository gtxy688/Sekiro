# 模块拆分方法

## 分层原则

按**依赖方向**分层，同层内模块可并行开发：

| 层 | 特征 | 典型内容 | 依赖 |
|----|------|---------|------|
| **基础层** | 无业务依赖，可并行 | 状态机框架、属性/数值、行为树框架、对象池 | 无 |
| **业务层** | 项目核心玩法 | 战斗判定、技能、背包、经济 | 基础层 |
| **控制层** | 把输入/AI 翻译为指令 | 输入系统、锁定、AI 决策 | 基础层 |
| **表现层** | 只消费事件，不反推逻辑 | 相机、UI、音效、特效 | 业务层事件 |
| **集成层** | 把各模块接到引擎/资源上 | 动画事件、场景装配、流程控制 | 业务层 |

关键：**表现层永远不反向依赖**。业务层不知道 UI 存在，UI 通过事件订阅业务层。

## 粒度判断

一个模块该拆的四个信号：

1. **能独立验收**——能在 Unity 里单独演示"做对了"的效果
2. **有清晰契约**——输入/输出可用一两句说清
3. **可单独重写**——推倒重来不影响其他模块接口
4. **规模适中**——单人 1～3 天可完成

不该拆的信号：

- 两个模块总是同时修改 → 应合并
- 模块只是"另一个模块的一部分" → 应下沉为子章节
- 拆开后需要大量跨模块私有访问 → 边界划错了

## 依赖图写法

用 ASCII 表达依赖方向，箭头指向被依赖方（A ──→ B 表示 A 依赖 B）：

```
M1 ──┬──→ M2 ──→ M3 ──→ M4 ──→ M5
     │           │
     │           └──→ M6 ──→ M7
     │
M8 ──┴──→ M9

表现层 M10/M11 订阅事件总线（不画入依赖图，或用虚线标注）
```

要点：
- 出现**环**就是设计问题，必须打破（通常是表现层反向依赖逻辑层）
- 把"订阅事件总线"的模块单独标注，它们不算编译期依赖

## 四种项目的分层示例

### 动作/ARPG
基础：状态机框架、属性系统、行为树 → 业务：命中判定、受击/弹反、架势、处决 → 控制：输入、锁定、Boss AI → 表现：相机、UI、音效 → 集成：动画事件、场景装配

### 卡牌/Roguelike
基础：卡牌数据（SO）、事件总线、对象池 → 业务：抽牌/弃牌堆、出牌结算、Buff/状态效果 → 控制：拖拽输入、敌人意图 AI → 表现：手牌 UI、伤害飘字、音效 → 集成：场景流程、存档

### 平台跳跃
基础：角色控制器、状态机、输入缓冲 → 业务：移动/跳跃手感、机关与陷阱 → 控制：关卡触发、检查点 → 表现：相机、粒子、音效 → 集成：关卡装配、UI 流程

### 模拟经营
基础：时间系统、资源数据（SO）、网格系统 → 业务：建造、生产链、经济 → 控制：放置输入 → 表现：网格渲染、面板 UI → 集成：存档、关卡配置

## 常见反模式

| 反模式 | 表现 | 修正 |
|--------|------|------|
| 一个"GameManager"包办一切 | 单文件上千行，改一处坏三处 | 按职责拆出独立管理器，用事件/中间层通信 |
| 表现层直接读逻辑层字段 | UI 每帧读 `player.hp` | 改为订阅血量变化事件 |
| 循环依赖 | A 引用 B，B 又引用 A | 抽出公共契约层，或让一方改为事件订阅 |
| 模块边界按技术而非业务 | 按"UI 层/逻辑层"横切所有玩法 | 按玩法纵向切分，每层内再分技术职责 |
| 一次性写完所有模块文档 | 写完即过时，实现时发现不对 | 需要实现哪个才展开哪个 |

## 编号约定

- 用 `M1/M2/…` 稳定标识，重命名模块时编号不变，避免文档引用失效
- 分层可调整顺序编号，但已定编号不再复用
- 模块删除时编号留空并注明，避免后续文档引用错位
