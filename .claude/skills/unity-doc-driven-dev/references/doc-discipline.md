# 文档访问纪律详解

## 为什么要约束文档访问

1. **上下文成本**：通读全部文档会挤占上下文，反而降低对关键细节的注意力
2. **过时文档风险**：旧文档可能与最新决策矛盾，读得越多，混入过时信息的概率越高
3. **幻觉源头**：文档缺失时，AI 倾向"合理推测"接口名与字段，产出无法编译或语义错误的代码
4. **边界污染**：跨模块阅读会让实现"顺手"改到别的模块，破坏模块契约

## 五条纪律与正反例

### 纪律 1：只读与任务相关的文档

- ❌ 反例：任务是"改技能冷却参数"，却把好几份模块的文档全读了一遍
- ✅ 正例：查索引表 → 技能系统属于 `0X-xxx.md` → 只读该文件相关章节

### 纪律 2：禁止跨模块引用

- ❌ 反例：写某模块逻辑时，引用了另一模块文档的字段命名约定
- ✅ 正例：只遵守本模块文档与项目统一代码规范

### 纪律 3：动手前先声明

- ❌ 反例：直接开始读文件、改代码，用户不知道 AI 依据的是哪份文档
- ✅ 正例："本任务要读 `Docs/architecture/0X-xxx.md`（该功能归属此模块），确认后开始"

好处：用户能在读错文档时立刻纠正，避免 AI 基于错误依据写完整个模块。

### 纪律 4：文档与代码冲突 → 停下报告，不自行选边

- ❌ 反例：文档说用状态模式，代码是平铺 switch，AI 自行按代码改
- ✅ 正例：列出冲突点（文档 X 节说 A，代码 Y 处是 B），请用户裁定，并说明两种走向的影响

### 纪律 5：缺失的文档或字段 → 停下询问，不臆造

- ❌ 反例：文档没写字段名，AI 自己起一个 `cooldownTimer`，与后续实际字段不一致
- ✅ 正例："架构文档未定义该字段命名，请确认；在此之前我不实现该字段"

## 索引表写法要点

索引表是纪律 1 的执行工具，质量直接决定定位效率：

1. **用任务关键词而非模块编号**
   - ❌ `M4 → 01-xxx.md`（要先知道某功能属于 M4）
   - ✅ `技能/冷却/消耗 → 01-xxx.md`（直接匹配任务描述）

2. **唯一映射**：一个任务类型只映射一份文档，避免"二选一"

3. **标注权威来源**：需求文档为唯一权威，用户决策记录标注"AI 不当规范用"

4. **覆盖高频任务**：把最近常做的任务类型放前面

## 文档冲突处理流程

```
发现冲突
  ├─ 停下手上的实现
  ├─ 列出冲突点：文档 A 第 X 节 vs 代码 Y 文件第 Z 行
  ├─ 说明两种走向的影响（改动量 / 是否破坏已有验收）
  └─ 等用户裁定 → 按裁定实现 → 同步更新文档
```

**不要**在实现过程中"先按我的理解做，回头再说"——改完后再对齐的成本远高于先问。

## 文档健康度维护

每次完成一个模块后检查：

- [ ] 实现与架构文档是否一致？不一致则更新文档或报告冲突
- [ ] 验收文档是否覆盖了本次改动？
- [ ] 索引表是否需要新增任务关键词？
- [ ] 需求文档的数值是否被复制到架构文档？（应引用，不复制）

## 何时可以不读文档

以下情况可直接实现，无需查文档：

- 纯重构且不涉及架构约定（如提取方法、重命名局部变量）
- 明确由用户当场给出的指令，且用户已说明不需要查文档
- 修复语法/编译错误

**不确定时，默认读文档。**
